# تنبيهات قرب انتهاء الحجز — 2026-08-12

## القرار المملوك

- التنبيه يشمل حجوزات `PHONE` و`WHATSAPP` فقط.
- حجوزات `STORE` و`WALK_IN` مستبعدة صراحةً.
- مفتاح الأتمتة العام هو `RESERVATION_NEAR_EXPIRY`، ويرتبط بإعداد مستقل
  `waHubSettings.flowReservationNearExpiry` معطّل افتراضياً مثل بقية الأتمتات.

## النمط المثبت

- `server/services/reservations/nearExpiry.ts` يسحب كل `ACTIVE` غير المنبّهة ضمن المجال المفتوح
  `NOW < expiresAt < NOW+4h` بصفحات keyset حجمها 200 مرتبة بـ`(expiresAt,id)`؛ المؤشر يتقدم حتى
  عند تخطي صف، فتظل ذاكرة العملية وعبارة `IN (...)` محدودتين ولا تحتكر الصفوف المتعذرة المقدمة.
- القالب `reservation_near_expiry` يستقبل بالترتيب: رقم الحجز، الاسم، ملخص الأصناف، ووقت الانتهاء
  `HH:mm` بتوقيت بغداد. قائمة الأصناف محدودة الطول مع إظهار عدد الباقي.
- `flowNotify` يبقى نقطة الإرسال الوحيدة: kill switch ثم مفتاح التدفق ثم التكامل النشط ثم opt-out ثم
  القالب المعتمد ثم outbox idempotent.
- دورة التنبيه تفحص الإعداد قبل المسح وتخرج إن كان المفتاح/الإيقاف العام معطلاً، وتشارك ذاكرة
  لبيانات التكامل المفكوكة بحسب الفرع والقالب بحسب الاسم/اللغة. يبقى `flowNotify` يعيد قراءة
  killSwitch لكل صف، ويتحقق باستعلام id خفيف أن التكامل المخبّأ ما زال `ACTIVE`؛ إن عُطّل أثناء
  الدفعة يتوقف فوراً، وإن استُبدل يعيد تحميل بياناته، من دون فك التوكن نفسه لكل صف.
  اعتماد القالب الإيجابي المخبأ يُعاد فحصه أيضاً لكل مرشح؛ تحوّله إلى PAUSED/REJECTED/DISABLED
  يوقف enqueue فوراً، بينما السالب يبقى بلا أثر وتعيد الدورة التالية المحاولة.
- البوابة لا تكتفي بحالة `APPROVED`: تقارن `waTemplates.variableCount` بعدد `bodyParams` قبل outbox؛
  القالب القديم أو الخاطئ لا يضع صفاً ولا أثر تنبيه، فيمكن إصلاحه وإعادة المحاولة.
- أرقام الحجز القديمة أو المدخلة محلياً تُطبّع عبر `normalizeIraqPhoneE164` قبل outbox.
  بعد التطبيع يجب أن تطابق E.164 (`+` ثم 8–15 رقماً)؛ المدخل المتسامح بلا أرقام يُتخطّى بلا أثر.
- الأثر الدائم `reservations.nearExpiryNotifiedAt` يخفّض إعادة المسح. مفتاح dedupe يتضمن id وموعد
  الانتهاء: `RESERVATION_NEAR_EXPIRY:{id}:{expiresAtMs}`.
- ترتيب المتانة هو outbox أولاً ثم الأثر: التعطل بينهما يعيد نفس صف outbox بلا ازدواج ثم يكمل الأثر.
  إن صار الصف نفسه `FAILED/CANCELLED` قبل الاستئناف، تعيده المحاولة المؤهلة ذرياً إلى `QUEUED`
  وتصفّر محاولاته وخطأه بدلاً من اعتبار duplicate نهائياً صفاً قائماً ووضع أثر كاذب.
- فحص الأهلية النهائي يقفل صف الحجز ويُنفَّذ داخل معاملة إدراج outbox نفسها؛ لا يستطيع التمديد أو
  الإلغاء العبور بين الفحص والجدولة. في الإنتاج تُعاد مقارنة النافذة بساعة MySQL الحالية (`NOW()`)
  لا بلحظة بدء الدورة؛ حقن `options.now` محصور في الاختبارات الحتمية. الإرسال الفوري لا يبدأ إلا بعد commit.
- تمديد الحجز يصفّر `nearExpiryNotifiedAt`؛ لأن موعد الانتهاء يدخل في dedupeKey، يحصل الموعد الجديد
  على تنبيه جديد حين يدخل نافذة الأربع ساعات.
- `startReservationsSweeper` يشغّل كروناً مستقلاً كل دقيقة، بقفل عدم تراكب مستقل، ويبقى استدعاؤه
  محصوراً بالعامل 0 عبر حارس `server/index.ts` الموجود مسبقاً.
- صفوف هذه الدفعة تُدرج `QUEUED` بلا dispatch فوري؛ كنّاس outbox يلتقط الصادر في الدقيقة التالية
  بحد `min(25, waHubSettings.throttlePerMinute)` كي لا تنطلق مئات طلبات Graph معاً. صفوف
  `MEDIA_FETCH` الواردة لها أولوية مستقلة عن حد الصادر وعن kill switch، بحد 20 كي تبقى خمس خانات
  للصادر، ومع بقاء سقف الدورة الكلي 25.
- عند تعدد الشركات، نقطة الدخول تلفّ الدورة تلقائياً بـ`runAcrossActiveTenants` قبل أي `requireDb`؛
  كل شركة تعمل داخل سياق ALS وقاعدة بياناتها، ثم تُجمع العدادات للتشخيص.
- outbox يحتفظ بـ`customerId` كمرجع منطقي بلا FK لإشعارات العملاء. قبل كل إرسال فعلي يعيد العامل
  قراءة العميل و`waConsent`؛ إن حُذف أو أصبح `OPTED_OUT` بعد الجدولة يُحوَّل الصف إلى `CANCELLED`
  بلا Graph. استخدام `ON DELETE SET NULL` هنا مصيدة: يمحو دليل أن الرسالة كانت مرتبطة بعميل محذوف.
- حمولة تنبيه الحجز تحمل `deliveryGuard` فيه id ولقطة `expiresAt`. العامل يعيد فحص الحالة والقناة
  والموعد والنافذة بساعة MySQL ومفتاح `flowReservationNearExpiry` قبل Graph، فيلغي الصف إن
  مُدّد/أُلغي/انتهى الحجز أو عُطّل التدفق أثناء انتظار الطابور.
- مفتاح التدفق ظاهر وقابل للحفظ في إعدادات الويب وAndroid الأصلية معاً.

## مصائد لاحقة

- لا تضع الأثر عند نتيجة `skipped`: قد يكون المفتاح أو التكامل أو القالب غير جاهز، ويجب أن تحاول
  الدورة التالية مجدداً.
- لا تستعمل `nearExpiryNotifiedAt` وحده كضمان idempotency؛ العطل بعد enqueue وقبل UPDATE يحتاج dedupe
  فريداً في outbox.
- لا تعِد استخدام dedupe ثابت للحجز عند التمديد؛ وإلا يمنع outbox تنبيه الموعد الجديد.
- لا توسّع الحالة إلى `PARTIALLY_FULFILLED` أو القنوات إلى `STORE/WALK_IN` بلا قرار مالك جديد.
- الاسم الفيزيائي لعمود حالة الحجز في SQL هو `reservationStatus` (لا `status`) رغم أن خاصية Drizzle
  اسمها `status`؛ الهجرات والفهارس اليدوية يجب أن تستعمل الاسم الفيزيائي.
- قالب Meta يجب أن يكون `APPROVED` باسم `reservation_near_expiry` ولغة `ar` وأربعة متغيرات بالترتيب
  أعلاه؛ غيابه يسبب skip آمن ولا يضع الأثر.
- لا تستدعِ dispatch الفوري لتدفق يُنشئ دفعة؛ `dispatchMode=DEFERRED` جزء من حماية المعدل.
- لا تُرجع استعلام المرشحين إلى `limit(200)` بلا keyset، ولا تزيل الحدّ كلياً: الأول يسبب starvation
  والثاني يصنع `IN` ضخمة واستهلاك ذاكرة غير محدود.
- لا تستعمل وقت بداية الدورة في الحارس الذرّي النهائي؛ قد ينقضي الحجز أثناء معالجة صفحات سابقة.
- لا تفحص opt-out عند الجدولة فقط: الصف المؤجل قد ينتظر، لذلك يجب حمل `customerId` وإعادة الفحص عند dispatch.
- القفل الذرّي عند enqueue لا يغني عن حارس dispatch للصف المؤجل؛ قد يتغير أصل الحدث بعد commit وقبل الكنّاس.
- أي cron مستأجر يعمل في worker 0 لا يعني تلقائياً وجود tenant ALS؛ لفّ نقطة الدخول متعددة الشركات
  قبل استدعاء `requireDb` وإلا يفشل الإنتاج متعدد المستأجرين فقط.
- لا تخلط `MEDIA_FETCH` الوارد مع طابور الصادر المرتب بالـid: تراكم الرسائل أو throttle منخفض يؤخر
  رابط الوسائط القصير العمر. افصل مسار الالتقاط وقدّمه، مع خصم سعته من سقف العامل الكلي وحجز سعة
  دنيا للصادر كي لا تجوع التنبيهات المؤجلة تحت سيل وسائط مستمر.
- لا تثق بذاكرة تكامل `ACTIVE` طوال دفعة طويلة؛ تعطيله أو استبداله في منتصفها يجب أن يُرى قبل enqueue
  التالي. خزّن السر المفكوك، لكن أعد التحقق بخفة من id والحالة لكل مرشح.
- لا تعتبر ناتج `normalizeIraqPhoneE164` صالحاً تلقائياً؛ الدالة متسامحة وتعيد النص المشذّب إن خلا
  من الأرقام. افحص E.164 قبل enqueue وإلا يُوضَع الأثر على إشعار سيرفضه Meta نهائياً.
- لا يكفي فحص مفتاح التدفق عند الجدولة: صف مؤجل قد يبقى بعد تعطيله، لذا افحص المفتاح داخل
  `deliveryGuard` عند dispatch وألغِ الصف قبل Graph.
- لا تحسب صفوف `CANCELLED` بالحارس ضمن `throttlePerMinute`: نظف مقدمة الطابور القديمة واستمر حتى
  حصة الإرسال الفعلي، مع سقف فحص مستقل (100) كي تبقى الدورة محدودة.
- لا تخبئ `APPROVED=true` للقالب طوال دورة طويلة بلا إعادة تحقق؛ مزامنة Meta قد تغيّر حالته بين صفين.
- لا تعتبر اعتماد القالب عقداً كافياً: طابق عدد متغيرات BODY مع الحمولة قبل تسجيل نجاح الجدولة.
- لا تعامل duplicate نهائياً (`FAILED/CANCELLED`) كأنه ما زال queued. أحيه فقط بعد اجتياز البوابات
  والحارس الذرّي الحالي، أو اترك أثر الحجز فارغاً.
