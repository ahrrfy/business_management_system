# 3 · عقد قرار الصلاحية (Authorization Contract)

> §30.3 — «المدخلات والنتائج والأولوية ودلالات الفشل». يفصّل §14 من الوثيقة الحاكمة ويسدّ
> ملاحظات ج-٣ (الأثر المتعدد)، ج-٥ (السياسة أثناء المعاملة)، د-٣ (تزامن CHALLENGE و PENDING).

## 3.1 المدخلات

```
AuthzRequest {
  principal: {
    type:       HUMAN | SERVICE | DEVICE | ANON | PLATFORM_ADMIN | SUPPORT_SESSION
    id:         معرّف الهوية
    tenantId:   المنشأة (حدّ صلب — لا يأتي من العميل)
    sessionId:  معرّف سطر الجلسة
    assurance:  { mfaVerified, mfaAt, reauthAt, passwordChangeRequired, enroll2FARequired }
    onBehalfOf: هوية المستخدم المستهدف عند جلسة الدعم (لا تستبدل الفاعل)
  }
  action:    كود الصلاحية الذرية `domain.resource.action`
  resource:  { type, id? , loadedAttributes? }   // المورد النهائي لا معرّف وسيط (§13.1)
  context:   { channel, requestId, traceId, at }
  hints:     { concurrencyToken? }               // تلميح عميل — ليس إصدار سياسة موثوقاً
}
```

**قواعد المدخلات:**

- `tenantId` و`branchId` و`ownerId` **لا تُقبل من العميل** أبداً (§12.3). تُقرأ من الجلسة أو
  من صفّ المورد المحمَّل خادمياً.
- إصدار السياسة **يختاره الخادم** دائماً (§14.1). تلميح العميل يُقارَن فقط؛ عدم التطابق ⇒
  إعادة تقييم بالإصدار النشط، أو رفض إن كانت العملية كتابية حسّاسة.
- `resource.id` وحده لا يكفي: يجب **تحميل المورد النهائي** قبل القرار لمنع IDOR عبر معرّف وسيط.

## 3.2 النتيجة

```
AuthzDecision {
  outcome:        PERMIT | DENY | CHALLENGE | PENDING_APPROVAL
  decisionId:     معرّف فريد
  reasonCode:     رمز ثابت (انظر 3.6)
  reasonAr:       نصّ عربيّ موجّه للمستخدم (بلا تفاصيل استكشافية)
  matchedGrants:  [ { source, roleAssignmentId?, grantId?, scopeId, policyId } ]
  matchedDenies:  [ ... ]
  effectiveScope: { tenantId, branchIds, orgUnitIds, ownership, warehouses, ... }
  rowFilter:      predicate مُنشأ خادمياً (لا SQL مخزَّن)
  fields:         { allowedRead[], allowedWrite[], masked[], maskStrategy }
  limits:         { maxAmount?, maxPercent?, currency?, periodCap? }
  obligations:    [ MFA_STEP_UP | REQUIRE_APPROVAL | REQUIRE_REASON | AUDIT_HIGH | NOTIFY ]
  sodConflicts:   [ { ruleId, kind, otherActorId?, recordId? } ]
  policyVersion:  الإصدار المستعمَل
  traceId:        معرّف التتبع
}
```

## 3.3 دلالات النتيجة (مُلزِمة)

| النتيجة | يسمح بالتنفيذ؟ | متى تصدر |
|---|---|---|
| `PERMIT` | **نعم — وهي الوحيدة** | وُجد statement كامل يغطي الفعل والمورد والقيم والحقول، ولا منع أعلى أولوية، وكل الالتزامات المانعة مستوفاة. |
| `DENY` | لا | لا مسار منحة صالح، أو منع مطابق، أو تعارض SoD، أو سمة مفقودة/مجهولة، أو خطأ سياسة. |
| `CHALLENGE` | لا | مسار منحة صالح مبدئياً + يلزم step-up MFA. |
| `PENDING_APPROVAL` | لا | مسار منحة صالح مبدئياً + يلزم اعتماد الطلب المحدد. |

**قاعدة الحسم (سدّ د-٣):** إذا لزم MFA **و** اعتماد معاً، النتيجة `CHALLENGE` أولاً. بعد استيفاء
MFA يُعاد التقييم فتصبح `PENDING_APPROVAL`. لا يُطلب اعتماد من جلسة لم تُثبت هويتها بالمستوى المطلوب.

**قاعدة غياب المنحة:** إذا لم توجد منحة أصلية، النتيجة `DENY` — **ولا يُعرَض MFA ولا الاعتماد**
كطريق للحصول على حق غير موجود (§14.2).

**منع الاختزال:** يجب أن يفحص PEP النتيجة typed كاملة. `if (decision)` أو `!== "DENY"` مخالفة.
تُكتشف بحارس CI ضمن §24.

## 3.4 الأثر المتعدد داخل الطلب الواحد (سدّ ج-٣)

نقطة الدخول ذات الآثار المتعددة (مثال قائم: مسار إرسال طلب المتجر = إنشاء فاتورة COD + خصم مخزون
+ إسناد مندوب) تُعالَج هكذا:

1. تُعلن نقطة الدخول **كل** صلاحياتها بدلالة `allOf` (§10.5).
2. يُقيَّم كل أثر بمدخلاته الخاصة (المورد الخاص به) ⇒ مجموعة نتائج.
3. **نتيجة الطلب = الأشدّ**، بالترتيب: `DENY` > `CHALLENGE` > `PENDING_APPROVAL` > `PERMIT`.
4. **لا يبدأ أي أثر** قبل أن تكون نتيجة كل الآثار `PERMIT`.
5. يُعاد فحص كل أثر عند نقطة حدوثه داخل المعاملة (شروط قابلة للتغيّر: الحالة، الرصيد، الحد).

## 3.5 السياسة أثناء المعاملة (سدّ ج-٥)

| الحدث | السلوك المُلزِم |
|---|---|
| نشر إصدار سياسة جديد أثناء طلب جارٍ | الطلب يلتقط `policyVersion` عند بدايته و**يكملها حتى نهاية معاملته**. الإصدار الجديد يسري على الطلبات التالية. |
| تعطيل مستخدم / إبطال جلسة / تسريب | **مقاطعة فورية**: المعاملة الجارية تُرجَع (ROLLBACK) والطلب يُرفض. |
| تغيير تعيين أو نطاق مستخدم | يسري على الطلبات التالية ضمن SLO الإبطال المعلن (§17). |
| فشل مصدر سمة أو كاش غير متسق | `DENY` آمن + تنبيه تشغيليّ (§14.2). |

هذا يتكامل مع `withTx` القائم: قرار التفويض يُلتقط قبل فتح المعاملة، ويُعاد فحص الشروط القابلة
للتغيّر **داخلها** تحت الأقفال (§13.3).

## 3.6 رموز السبب (reasonCode) — مجموعة مغلقة

| الرمز | المعنى | النتيجة |
|---|---|---|
| `NO_GRANT` | لا منحة تغطّي الفعل | DENY |
| `SCOPE_MISMATCH` | المنحة لا تغطّي نطاق المورد | DENY |
| `TENANT_BOUNDARY` | تجاوز حدّ منشأة | DENY |
| `EXPLICIT_DENY` | منع صريح مطابق | DENY |
| `HARD_DENY_ORG` | منع مؤسسيّ صلب | DENY |
| `SOD_STATIC` / `SOD_DYNAMIC` / `SOD_OBJECT` / `SOD_HISTORICAL` | تعارض فصل مهام | DENY |
| `CONDITION_FAILED` | شرط لم يتحقق (حالة/وقت/قناة) | DENY |
| `LIMIT_EXCEEDED_HARD` | تجاوز حدّ بسلوك «رفض» | DENY |
| `FIELD_FORBIDDEN` | حقل غير مسموح في الكتابة | DENY |
| `ATTRIBUTE_MISSING` / `ATTRIBUTE_STALE` | سمة مفقودة أو قديمة | DENY |
| `POLICY_UNKNOWN` / `POLICY_ERROR` | سياسة/صلاحية غير مسجّلة | DENY |
| `USER_DISABLED` / `SESSION_INVALID` / `ROLE_INACTIVE` | حالة هوية | DENY |
| `MFA_REQUIRED` / `MFA_STALE` / `REAUTH_REQUIRED` | يلزم step-up | CHALLENGE |
| `APPROVAL_REQUIRED` / `LIMIT_EXCEEDED_APPROVABLE` | يلزم اعتماد | PENDING_APPROVAL |
| `PERMIT_ROLE` / `PERMIT_DIRECT` / `PERMIT_DELEGATION` / `PERMIT_BREAKGLASS` | مصدر السماح | PERMIT |

## 3.7 ترتيب التقييم (تنفيذ §14.4)

```
1  تثبيت المنشأة وحدّ الثقة                       → TENANT_BOUNDARY
2  حالة المستخدم/الجلسة/كلمة المرور/التسجيل بـ2FA → USER_DISABLED | SESSION_INVALID
3  تسجيل الفعل والمورد ونقطة الدخول               → POLICY_UNKNOWN
4  تحميل المورد النهائي + السمات الموثوقة          → ATTRIBUTE_MISSING | ATTRIBUTE_STALE
5  المنع المؤسسي الصلب + SoD                      → HARD_DENY_ORG | SOD_*
6  المنع الصريح المطابق للنطاق                    → EXPLICIT_DENY
7  توليد statements لكل تعيين/منحة/تفويض (بأبعادها كاملة)
8  تقييم النطاق والعلاقات والشروط + جبر الدمج (§14.3)
9  قيود الحقول والقيم                             → FIELD_FORBIDDEN | LIMIT_EXCEEDED_*
10 تحديد الالتزامات                               → MFA_* | APPROVAL_REQUIRED
11 لا مسار سماح كامل ⇒ DENY افتراضي               → NO_GRANT | SCOPE_MISMATCH
12 كل الالتزامات مستوفاة ⇒ PERMIT، وإلا CHALLENGE/PENDING_APPROVAL
13 الإنفاذ داخل الاستعلام/الخدمة/المعاملة
14 تسجيل القرار
```

## 3.8 الأولوية (تنفيذ §14.5)

```
حدّ المنشأة  >  منع مؤسسي صلب / SoD  >  منع صريح مقيَّد بالنطاق  >  منح
```

- الموافقة **لا تتغلب** على غياب الصلاحية.
- MFA **لا يمنح** صلاحية.
- المنحة المباشرة **لا تتغلب** على منع صلب.
- عند تعدّد سياسات الجلسة ⇒ يُطبَّق **الأكثر تقييداً**.
- عند تطابق عدة مسارات على المورد نفسه ⇒ قواعد دمج محددة النوع ومختبَرة؛ **ممنوع** اختيار المسار
  الأقلّ التزامات للتهرّب من MFA أو الاعتماد (§14.3.8).

## 3.9 دلالات الفشل

| الحالة | السلوك |
|---|---|
| صلاحية غير مسجّلة | DENY + تنبيه (**فشل مغلق**، §8.1) |
| سمة مجهولة/قديمة/غير صالحة النوع | DENY + تنبيه |
| إصدار سياسة غير معروف | DENY + تنبيه |
| PDP غير متاح | **DENY** — لا fallback إلى النظام القديم الأوسع (§29.19) |
| دور مفقود/معطّل | `NO_ACCESS/QUARANTINED` لا هبوط لدور قراءة (§11.6) |
| تعارض بين معاينة/محاكي والخادم | يُعامَل عيباً حاصراً (§25.8) |

## 3.10 عقد الواجهة

- الواجهة تستهلك **نتيجة** القرار (مصفوفة القدرات الفعلية للجلسة) لتحسين التجربة فقط (§8.3).
- **ممنوع** أن تحسب الواجهة قراراً بمنطق موازٍ — هذا هو نمط الخطأ الحاليّ
  (`hasModuleAccess` مشتركة، لكنها منطق مكرَّر لا نتيجة محسوبة خادمياً).
- المحاكي يستدعي **محرك القرار نفسه** (§21.4).
