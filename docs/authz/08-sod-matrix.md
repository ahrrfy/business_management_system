# 8 · مصفوفة فصل المهام (SoD Matrix)

> §30.8 — «التعارضات الساكنة والديناميكية والاستثناءات».
> **الحالة: مسودّة تحتاج اعتماد مالك كل عملية ومالك المخاطر** (§16.2 الفقرة الأخيرة، §31.2).

## 8.1 الأنواع الأربعة (§16.1)

| النوع | الفحص | المتى |
|---|---|---|
| **ساكن** (Static) | السلطة الفعالة **المجمَّعة** عبر كل الأدوار والمجموعات والمنح المباشرة والمؤقتة والتفويضات، متى تداخلت نطاقاتها | عند تكوين الدور وعند التعيين |
| **ديناميكي** (Dynamic) | منع تنفيذ خطوتين متعارضتين في العملية نفسها | عند تنفيذ المعاملة |
| **على مستوى الكائن** (Object) | القدرتان مسموحتان عموماً، ممنوعتان على **السجل نفسه** | عند تنفيذ المعاملة |
| **تاريخي** (Historical) | منع خطوة لاحقة بناءً على أفعال سابقة على السجل | عند تنفيذ المعاملة |

⚠️ **الفحص الساكن لا يقتصر على الدور الواحد.** الخطأ الشائع: فحص التوليفة داخل دور، فيتهرّب
المستخدم بتعيينين. النموذج الحاليّ (`detectSodConflicts` في `shared/capabilities.ts:134`) يفحص
مجموعة قدرات فعّالة واحدة — صحيح مفاهيمياً، لكن غير موصول ولا يعرف التعيينات المتعددة (غير موجودة بعد).

## 8.3 التعارضات الديناميكية والكائنية — المطبَّقة اليوم

النظام يطبّق فعلاً «منشئ ≠ معتمِد» في مواضع، وهذا يُحفَظ:

| الموضع | القاعدة | الشاهد |
|---|---|---|
| سندات الصرف | اعتماد ثانٍ فوق العتبة + **دائماً** لمودِعي الأمانة | `voucherService` + شريحة الأمانة ٥ |
| تسوية المخزون | طلب ⇐ اعتماد مدير آخر + فحص تفاؤليّ على الرصيد | `stockAdjustmentRequests` (0082) |
| الجرد | منشئ ≠ معتمِد، عادّ ≠ معتمِد، **توقيعان دائماً** | جرد الافتتاح |
| العمولات | معتمِد ≠ محتسِب + حارس مسيّر معتمد | وحدة العمولات |
| تسوية نهاية الخدمة | سند صرف `PENDING_APPROVAL` دائماً | PR #232 |

**الثغرة البنيوية:** كل واحدة مطبَّقة **داخل خدمة مجالها** بمنطق خاص. لا سجلّ SoD مركزيّ،
ولا فحص ساكن عند تكوين الدور، ولا استثناء admin موحَّد. لهذا:

- إضافة عملية حسّاسة جديدة **لا ترث** SoD تلقائياً.
- لا يمكن الإجابة عن «من يجمع سلطتين متعارضتين؟» بلا مسح يدويّ.
- استثناء admin مختلف من موضع لآخر.

## 8.4 الاستثناءات (§16.3)

| القاعدة | التطبيق |
|---|---|
| لا تجاوز صامت لـadmin | ⚠️ **مخالَف اليوم**: `admin` يعبُر كل بوّابة (`trpc.ts:53,75,86`)، و`isOwner` يتجاوز الاعتماد الثنائي. |
| منشأة صغيرة ⇒ استثناء مؤقت بضوابط تعويضية | ✅ مناسب لواقع المشروع (فرعان، فريق صغير) — **هذا هو المسار الصحيح لـ`isOwner`** |
| الاستثناء يحتاج: سبباً + مدة + MFA + موافقة + تنبيهاً + مراجعة لاحقة | ❌ لا شيء من ذلك اليوم |
| لا يعتمد المستخدم استثناءه بنفسه | ❌ غير مفروض |

### النموذج المقترح لاستثناء SoD

```
SodException {
  ruleId, principalId, scope,
  reason (إلزاميّ، نصّ حرّ ≥ 20 حرفاً),
  validFrom, validUntil (إلزاميّ، ≤ 90 يوماً),
  requiresMfaAtUse: true,
  approvedBy (≠ المستفيد), approvedAt,
  compensatingControls[] (مثل: إشعار فوريّ للمالك + مراجعة أسبوعية),
  reviewedAt, reviewOutcome
}
```

**تطبيقه على `isOwner`** (ح-١، خيار «أ»): يتحوّل العَلَم من تجاوز دائم صامت إلى استثناء SoD
معتمَد ذي مدة وسبب وتنبيه ومراجعة — بلا فقدان قدرة المالك على العمل، ومع أثر تدقيقيّ كامل.
**البديل (خيار «ب»)**: إلغاؤه واستبداله بـbreak-glass عند الحاجة. **قرار مالك.**

## 8.5 قواعد الإنفاذ

1. **الفحص الساكن عند تكوين الدور وعند التعيين** — يُرفض الحفظ الذي ينتج توليفة سامّة، مع بيان
   الطرفين ومصدر كلٍّ (§21.5).
2. **الفحص الديناميكي/الكائنيّ داخل المعاملة تحت القفل** — لا قبلها (منع سباق «إنشاء واعتماد
   متزامنين»، §24.6).
3. **SoD أعلى من كل منح عادية** وأدنى من حدّ المنشأة فقط (§14.5).
4. **الموافقة لا تُسقط SoD** — المعتمِد نفسه يخضع للقاعدة.
5. **كل تعارض يظهر في `sodConflicts` داخل قرار التفويض** مع `ruleId` والطرف الآخر (§3.2).
