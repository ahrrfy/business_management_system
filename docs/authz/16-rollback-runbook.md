# 16 · دليل التراجع (Rollback Runbook)

> §30.16 — «خطوات رجوع مجرَّبة لكل موجة». مُلزِم: **لا cutover لموجة قبل تمرين تراجع ناجح فعلياً**
> (§23-م5 بوابة الخروج، §25.25).

## 16.1 مستويات التراجع الأربعة

| المستوى | ما يُتراجَع عنه | الزمن المستهدف | من يقرّر |
|---|---|---|---|
| **R1** | إصدار سياسة (بيانات فقط) | ≤ 2 دقيقة | مسؤول النشر |
| **R2** | وضع الإنفاذ (`on` → `dual` → `shadow`) | ≤ 5 دقائق | مسؤول النشر + قائد التطوير |
| **R3** | نشر كود (PM2 reload لإصدار سابق) | ≤ 15 دقيقة | قائد التطوير + مالك المنظومة |
| **R4** | هجرة مخطط | ≤ 60 دقيقة | مالك المنظومة (**نادر جداً**) |

**قاعدة الاختيار:** ابدأ دائماً من أدنى مستوى يعالج المشكلة. R4 آخر الملاذات.

## 16.2 R1 — تراجع إصدار سياسة

**متى:** توسّع صلاحيات غير مقصود · رفض خاطئ واسع · تعارض SoD ظهر بعد النشر.

```
1. تجميد النشر:            AUTHZ_POLICY_FREEZE=on
2. تحديد الإصدار السليم:   آخر publication حالته HEALTHY
3. تنفيذ التراجع:          publishPolicyVersion(<previous>, reason, actor)
4. إبطال الكاش:            انتظر SLO (≤ 5 ثوانٍ) ثم تحقّق من كل worker
5. تحقّق:                  المحاكي على 5 حالات مرجعية ⇒ نتائج ما قبل النشر
6. رفع التجميد + تقرير حادثة
```

**لا يلمس الكود ولا المخطط.** هذا هو المسار المتوقَّع لـ95% من الحوادث.

⚠️ **الرجوع إلى إصدار سياسة سليم — لا إلى legacy** (§29.19).

## 16.3 R2 — خفض وضع الإنفاذ

**متى:** خلل في المحرك نفسه لا في السياسة · تجاوز ميزانية الأداء · فشل إبطال الكاش.

```
on  →  dual     (legacy && new — أضيق التقاطعَين، آمن)
dual →  shadow  (القديم ينفّذ، الجديد يسجّل)
```

⚠️ **الخفض إلى `shadow` يعيد سلطة legacy الأوسع.** لذا هو **مسموح فقط**:
- في موجة لم تُنجَز فيها إصلاحات الانحرافات P0 بعد، **أو**
- بقرار صريح من مالك المنظومة مع تسجيل السبب وإشعار فوريّ.

في موجة أُغلقت انحرافاتها P0، الخفض المسموح هو `on → dual` فقط. تجاوز ذلك ⇒ `AUTHZ_KILL_SWITCH`
(فشل مغلق على الفعل الحسّاس) لا العودة إلى القديم.

## 16.4 R3 — تراجع نشر الكود

```
1. تأكيد أن R1/R2 لا يكفيان
2. تحديد آخر commit مستقرّ (prod=<sha>)
3. على الخادم:  git checkout <sha> && pnpm install --frozen-lockfile && pnpm build && pm2 reload
   (أو إعادة تشغيل pnpm prod:deploy على الوسم السابق — نفس المسار الذرّي)
4. ⚠️ الهجرات لا تُتراجَع في هذه الخطوة — النموذج الجديد مُضاف بجانب القديم فيبقى خاملاً بلا أثر
5. تحقّق: /healthz = 200 · دخول فعليّ · بيع اختباريّ · اعتماد سند اختباريّ
6. تقرير حادثة
```

**الشرط الذي يجعل R3 آمناً:** جداول النموذج الجديد **مُضافة لا مُستبدِلة** حتى م8. الكود القديم
لا يقرأها ⇒ وجودها بلا ضرر.

## 16.5 R4 — تراجع هجرة مخطط

**نادر — يُتجنَّب بالتصميم.** كل هجرة في هذه الحملة يجب أن تكون:

- **إضافية فقط** (`CREATE TABLE` / `ADD COLUMN`) — لا `DROP` ولا `MODIFY` على أعمدة قائمة.
- **قابلة للتراجع** بعبارة عكسية موثَّقة ومُختبَرة على قاعدة خدش.
- **INSTANT** حيثما أمكن (تجنّب قفل جدول على الإنتاج).

```
1. pnpm db:backup                     (إلزاميّ قبل أي لمسة)
2. تأكيد أن لا كتابة نشطة على الجداول المستهدفة
3. تطبيق الهجرة العكسية الموثَّقة
4. pnpm db:verify                     (13 فهرساً حرجاً + سلامة المخطط)
5. تحقّق وظيفيّ كامل
```

⚠️ **فخّ موثَّق في هذا المشروع:** `db:push` التزايديّ على قاعدة منجرفة يفشل على MySQL 8.4
(`ER_DROP_INDEX_FK`) فيتجمّد المخطط. **لا `db:push` على الإنتاج إطلاقاً** — الهجرات ملفّات SQL
مولَّدة عبر migrator.

## 16.6 تمرين التراجع — إلزاميّ لكل موجة

**لا يُقبل «موثَّق». يجب أن يُنفَّذ فعلياً.**

| الخطوة | الدليل المطلوب |
|---|---|
| 1. نشر إصدار سياسة يحوي خطأً متعمّداً في بيئة staging | لقطة الإصدار |
| 2. رصد الخطأ عبر لوحة الاختلافات/التنبيهات | لقطة التنبيه + الزمن |
| 3. تنفيذ R1 | سجلّ التراجع + الفاعل + الوقت |
| 4. قياس زمن الاستعادة الفعليّ | مقارنة بالهدف (≤ 2 دقيقة) |
| 5. تحقّق من عودة القرارات | 5 حالات مرجعية عبر المحاكي |
| 6. تكرار مبسّط لـR2 و R3 | سجلّ |

**بوابة القبول:** تمرين ناجح موثَّق بالزمن الفعليّ ≤ 30 يوماً قبل cutover الموجة.

## 16.7 الحالات التي **لا** تُعالَج بالتراجع

| الحالة | الإجراء الصحيح |
|---|---|
| توسّع صلاحيات **اكتُشف بعد استغلاله** | تراجع + **إبطال الجلسات المتأثرة** + مراجعة أمنية + تقرير حادثة |
| تسريب بيانات عبر تصدير مسموح خطأً | تراجع + جرد ما صُدِّر من سجلّ التدقيق + إخطار |
| قرار خاطئ **كتب** أثراً مالياً | تراجع لا يعكس الأثر — يلزم **تصحيح محاسبيّ** (سند/قيد عكسيّ) بمسار المجال |
| فقد سجلّ قرارات | تراجع لا يستعيده — يلزم تحقيق في مسار التسجيل |

⚠️ الصفّ الثالث حاسم: **التفويض قابل للتراجع، والأثر المالي لا.** لهذا `dual` (`legacy && new`)
هو الوضع الافتراضي للأفعال الحسّاسة أثناء الانتقال — التقاطع لا يوسّع أبداً.

## 16.8 قائمة تحقّق ما قبل كل cutover

- [ ] تمرين R1 ناجح موثَّق بالزمن (≤ 30 يوماً)
- [ ] تمرين R2 ناجح
- [ ] `pnpm db:backup` منفَّذ ومُتحقَّق منه
- [ ] آخر commit مستقرّ معروف ومُسجَّل (`prod=<sha>`)
- [ ] الهجرة العكسية موثَّقة ومُختبَرة على قاعدة خدش
- [ ] مسؤول النشر ومسؤول التراجع مُسمَّيان ومتاحان
- [ ] قناة إشعار الحادثة جاهزة
- [ ] معايير الإيقاف (§15.5) مُراقَبة آلياً لا يدوياً
- [ ] لا وردية مفتوحة لعملية حسّاسة وقت النشر
