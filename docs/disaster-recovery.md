# دليل التعافي من الكوارث — نظام الرؤية العربية

> ماذا تفعل عند فقد البيانات أو تعطّل القاعدة. اقرأه **قبل** الكارثة، لا بعدها.

## ١. الترحيل الآمن من الحاوية القديمة (بلا volume) إلى docker-compose

الحاوية `erp-mysql` القديمة أُنشئت بلا named volume ⇒ بياناتها داخل طبقة الحاوية القابلة للحذف.
هذا الإجراء ينقلها إلى `erp_data` volume دائم **دون فقد**. نفّذه مرّة واحدة:

```powershell
# 1) نسخة احتياطية كاملة أوّلاً (الأمان قبل كل شيء)
pnpm db:backup
$env:MYSQL_PWD=$env:DB_ROOT_PW
docker exec -e MYSQL_PWD erp-mysql mysqldump -uroot --all-databases --single-transaction --routines --events > full-dump.sql

# 2) أوقف الحاوية القديمة وأعد تسميتها (لا تحذفها بعد — شبكة أمان)
docker stop erp-mysql
docker rename erp-mysql erp-mysql-old

# 3) ارفع الحاوية الجديدة بالـvolume الدائم
docker compose up -d
docker compose ps          # انتظر "healthy"

# 4) استورد البيانات إلى الحاوية الجديدة
docker exec -i -e MYSQL_PWD erp-mysql mysql -uroot --binary-mode=1 < full-dump.sql
pnpm db:ensure-app-user

# 5) تحقّق التكامل
# تحقق قراءة من المخطط والمستندات؛ اختبارات التطبيق لها قاعدة مستقلة لأنها قد تفرغ الجداول
#    + جولة بصرية: افتح اللوحة وتأكّد من ظهور المنتجات/الفواتير

# 6) بعد ٧ أيام من الاستقرار فقط، احذف القديمة
docker rm erp-mysql-old
```

## ٢. استعادة من نسخة احتياطية

```powershell
# اعرض النسخ المتاحة (الأحدث أسفل)
dir backups\

# نافذة صيانة إلزامية: أوقف عمال الويب ثم استعمل المسار المحصّن الوحيد.
pm2 stop erp-server
pnpm db:restore backups\erp-2026-06-07T02-00-00.sql --confirm RESTORE
# السكربت يأخذ نسخة أمان، يتحقق من هوية القاعدة، يطبّق الهجرات ويفحص المخطط.
pm2 start erp-server
pnpm db:verify
```

### استعادة نسخة خارجية مشفّرة (VPS)

النسخ الخارجية تُسحب مشفّرة (`.sql.gpg`). فكّ التشفير أولاً ثم استعد كالمعتاد:

```bash
gpg -d -o restore.sql erp-2026-06-10T23-00-00.sql.gpg   # يطلب BACKUP_GPG_PASSPHRASE
pm2 stop erp-server
pnpm db:restore restore.sql --confirm RESTORE
pm2 start erp-server
```

> **استعادة نقطة-زمنية (binlog):** قاعدة الـVPS تحتفظ بـbinlog لثلاثة أيام، فبعد استعادة آخر نسخة
> ليلية يمكن إعادة تطبيق الحركات حتى لحظة العطل عبر `mysqlbinlog --start-datetime=…` —
> إجراء دقيق؛ اطلبه من المهندس ولا تنفّذه ارتجالاً.

## ٣. إثبات الاستعادة في بيئة مستقلة

**سلامة النقل ليست نجاح استعادة.** ملف `.sql.gpg.manifest.json` يثبت حجم وبصمة الملف المنشور بعد نجاح التشفير؛ حقله `recovery.status=NOT_RESTORE_VERIFIED` لا يتحول إلى نجاح بمجرد نسخ الملف أو فحص صحته. صحة فك GPG لا تثبت اكتمال الجداول أو صلاحية تسجيل الدخول.

- لا تُجرَّب الاستعادة داخل حاوية الإنتاج أو مرآته، ولا داخل قاعدة تملكها جلسة أخرى. لا تُنقّى SQL بأمر `grep` ثم يُفترض أنها آمنة؛ النسخ الحديثة محايدة الهدف، والنسخ القديمة تحتاج مسار الاستعادة المحروس وفحص جميع محددات الهدف.
- لا تشغّل `pnpm test` على قاعدة مستعادة للاحتفاظ: تهيئة اختبارات التطبيق قد تفرغ الجداول. الاختبارات الآلية لها قاعدة منفصلة عن النسخة المستعادة.
- سكربت `backup-restore-drill.mjs` الحالي ينشئ ويحذف قاعدة تمرين، ومسار GPG فيه يستخدم argv واسم plaintext متوقعاً. **لا يُستخدم ضمن تفويض «دون حذف»، ولا لإثبات الاستعادة الخارجية قبل معالجة هذا المسار والتحقق منه.** لم يعدّل ضمن شريحة حماية النقل.
- يلزم تمرين منفصل مصرّح به في حاوية معزولة الهوية والشبكة، بمفاتيح من escrow وليس الخادم القديم، مع مخرجات فريدة وحفظ/تنظيف محكوم. لا تبديل مفاتيح التشفير القديمة؛ `INTEGRATIONS_ENCRYPTION_KEY` جزء من استعادة التكاملات وTOTP.

### مجموعة الاستعادة المطلوبة

بيان تحقق مستقل يربط: اسم وبصمة وحجم DB المشفر، بصمة SQL بعد الفك، رأس التطبيق وقفل الحزم، سجل الهجرات الفعلي، manifest الوسائط وبصماتها، مراجع escrow دون قيم أسرار، ونقطة binlog إن كان الاسترداد النقطي مطلوباً. metadata المنشورة مع النسخ لا تغني عن هذا البيان؛ `source.revision=null` أو `mediaManifest=null` تعني فجوة معلنة.

بوابة نجاح التمرين: استعادة المخطط والبيانات، تحقق قراءة من المستندات والذمم والمخزون/التكلفة والقيود، تسجيل دخول وTOTP وفك سر تكامل ممثل دون إرساله، عرض وسائط/مستند ممثل، ومنع إرسال إشعارات أو تشغيل عمال أو تنفيذ دفع خارجي في المختبر. يُسجل RPO من وقت أخذ النسخة وRTO حتى قابلية الخدمة المطلوبة، لا زمن استيراد SQL وحده.

**الدليل التاريخي فقط:** تمرين25 أكتوبر استعاد SQL محلياً إلى قاعدة اختبار (330 جدولاً، نحو207ث). الجولة المحلية30 أكتوبر استعملت `scripts/isolated-local-restore.mjs` على نسخة مشفرة محلية مؤرخة29 أكتوبر: نجح فكها واستيراد367 جدولاً وقراءة الجداول الأساسية، والتحقق من28 قيمة مشفرة بالمفتاح المحلي. حاويتها جديدة بلا شبكة أو منافذ أو ربط مضيف، متوقفة ومحفوظة بلا حذف. هذا إثبات لاستعادة SQL ومطابقة المفاتيح لهذه اللقطة؛ لا يُعد تعافياً كاملاً للتطبيق أو صور R2. التفاصيل والقيود في [سجل المرحلة0/1](backup-recovery-stage0-2026-10-30.md).

المسار الجديد يتطلب مصدراً محلياً صريحاً (`--encrypted` أو `--sql`)، ومجلد أدلة جديداً (`--evidence`)، ومحرك Docker محلياً (`--context`). لفك التشفير يلزم `--gpg` و`--secrets-file`؛ ولنسخة Git على Windows يضاف `--gpg-msys`. لا يحمل إعداد اتصال القاعدة من ملف الأسرار، ولا يشغّل التطبيق أو عماله. يحفظ SQL المفكوك وكلمة مرور المختبر في مجلد الأدلة المحلي؛ لذلك يعامل هذا المجلد كبيانات حساسة ولا يرفع إلى Git أو CI. لا إزالة تلقائية للحاوية أو وحدتها أو الأدلة. إعادة الاختبار تنشئ مختبراً جديداً، فلا تكررها دون سبب.

### نشر بروتوكول سلامة النسخ لاحقاً والرجوع

1. المنتج أولاً: `backup.mjs` ينشر التشفير باسم مؤقت ثم manifest أخيراً. يحتفظ بعقد SQL المحلي و`--no-rotate` للمستهلكين. إخفاق التشفير/المرايا يجعل الخروج فشلاً مع حفظ SQL.
2. المستهلكان معاً: `pull-vps-backup.ps1` و`health-check-local.ps1` يعتمدان `scripts/lib/offsite-integrity.ps1`. نسخ ملفي PS دون المكتبة غير صالح. يجب التأكد من وجود نسخة حديثة بmanifest قبل تفعيلهما؛ لا تجريبها على الإنتاج ضمن العمل المحلي.
3. الملفات القديمة بلا manifest تبقى محفوظة و«غير متحققة»، ولا يكتب لها نجاح بأثر رجعي من مجرد وجودها. السحب يعيد نقل غير المطابق إلى ملف مؤقت، ويحفظ القديم باسم unverified بدلاً من حذفه. الخلفية القديمة بلا دليل تؤجل مع تحذير؛ الأحدث بلا دليل يفشل مغلقاً.
4. `BACKUP_OFFSITE_DIR` يستقبل أحدث نسخة مشفرة متحققة عبر المسار الجديد؛ النسخ السابقة لا تُحذف. مراجعة المرايا التاريخية غير الموثقة عمل مستقل؛ لا ادعاء سلامتها من وجودها. إذا تعارض ملف مرآة قائم مع النسخة المتوقعة، يفشل النقل ويحفظ الطرفين للتحقيق.
5. التدوير التلقائي من `backup.mjs` والسحب **معلق** حتى اعتماد سياسة تحفظ آخر مجموعة استعادة مثبتة. `KeepLocal` بقي للتوافق ولا ينفذ حذفاً. أمر `backup-rotate.mjs` المباشر القديم لم يُحصّن في هذه الشريحة؛ لا يُستخدم كمسار بديل، وتُراجع أي جدولة مستقلة له قبل النشر. نمو التخزين مقابل الحماية قرار ظاهر يجب مراقبته، لا تعطيل صامت للنسخ الخارجي.
6. الرجوع يعيد التطبيق/الإعداد المتوافق ولا يحذف SQL أو ciphertext أو partial أو receipts. إعادة المنتج القديم تجعل نسخه اللاحقة بلا marker فتفشل الصحة الجديدة؛ هذا فشل صريح متوقع، وليس مبرراً للرجوع إلى نجاح الوجود فقط. لا تُخفض معيار التحقق عند الرجوع، ولا تستعد قاعدة قديمة فوق معاملات جديدة.

## ٤. سيناريوهات الطوارئ

| العطل | الإجراء |
|---|---|
| **الحاوية لا تبدأ** | `docker compose logs mysql` لمعرفة السبب؛ إن كان Docker Desktop ساقطاً: أعد تشغيله ثمّ `node scripts/docker-watchdog.mjs`. |
| **فقد البيانات (حذف/تلف)** | استعد من آخر نسخة (§٢). البيانات منذ آخر نسخة تضيع — لذا النسخ اليومية مهمّة. |
| **تلف الجهاز كاملاً (متجر محلي)** | جهاز جديد ⇐ `docs/redeploy.md` + استعادة آخر نسخة من `BACKUP_OFFSITE_DIR` (OneDrive/USB). |
| **فقد الـVPS كلياً (احتراق/حذف/اختراق)** | خادم جديد ⇐ `docs/deployment-vps.md` من الصفر، ثم فكّ آخر نسخة مسحوبة على جهاز المتجر (`~/erp-vps-backups/*.sql.gpg`) بعبارة GPG **من الـescrow** واستعادتها. يتطلّب أسرار الـescrow أدناه — بدونها النسخ الخارجية لا تُفتح. |
| **`docker rm` بالخطأ** | الـvolume `erp_data` يبقى! `docker compose up -d` يعيد ربطه بالبيانات سليمة. (هذا هو سبب وجود الـvolume.) |
| **حذف الـvolume بالخطأ (`down -v`)** | استعد من نسخة (§٢). لهذا لا تستعمل `down -v` أبداً. |

## ٤.١ — Escrow الأسرار (إلزامي قبل اعتبار النشر مكتملاً)

النسخ الخارجية مشفّرة، والمفاتيح تعيش في `.env` على الخادم نفسه — **يوم يُفقد الخادم تُفقد معه ما لم
تكن محفوظة خارجه**. احفظ هذه الأسرار في مكانين مستقلّين على الأقل (مدير كلمات مرور المالك + ورقة
في خزنة المتجر):

| السرّ | لماذا يلزم يوم الكارثة |
|---|---|
| `INTEGRATIONS_ENCRYPTION_KEY` | المفتاح الأصلي لفك الحالة المشفرة والتكاملات وTOTP؛ توليد مفتاح جديد لا يفك القديم |
| `BACKUP_GPG_PASSPHRASE` | بدونها كل ملفات `.sql.gpg` الخارجية **حبر على ورق** |
| `DB_ROOT_PW` | الاستعادة وإدارة القاعدة على الخادم الجديد |
| `JWT_SECRET` | إن أُعيد استعماله تبقى جلسات المستخدمين صالحة؛ وإلا فدخول جديد للجميع (مقبول) |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | أول دخول بعد الاستعادة |

**واختبر فعلياً** (مرة بعد النشر ثم ربع سنوياً): فكّ نسخة `.sql.gpg` على جهاز المتجر بالعبارة
المحفوظة في الـescrow — لا بالعبارة الموجودة على الخادم. عبارة منسوخة خطأً تُكتشف اليوم، لا يوم الحريق.

## ٥. مؤشّرات صحّة يجب مراقبتها

- حجم آخر نسخة احتياطية **يتزايد** بمرور الوقت (تقلّصه = إنذار فقد بيانات).
- عمر أحدث ملف في `backups\` **< ٢٤ ساعة** (وإلّا الجدولة معطّلة).
- وجود نسخة في `BACKUP_OFFSITE_DIR` بعمر < ٢٤ ساعة.
- `docker compose ps` تُظهر `healthy` لا `unhealthy`.
