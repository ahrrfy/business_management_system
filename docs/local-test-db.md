# تهيئة قاعدة الاختبار المحلّية (Local Test DB) — MySQL 8.4.9

> **الخلاصة العملية:** إن سقط `pnpm test` (أو `pre-commit`) بأخطاء `Unknown column '...'` لا علاقة لها
> بالكود الذي تُعدّله، فقاعدة الاختبار المحلّية متجمّدة خلف المخطّط. الحلّ بأمرٍ واحد:
> ```
> pnpm test:db:init
> ```
> ثم `pnpm test`. لا تُصلحها بإضافة أعمدة يدوياً ولا بـ`db:push` تزايديّ.

---

## ١. الأعراض

- الحزمة الكاملة (`pnpm test`) و‎`.husky/pre-commit` (`pnpm check && pnpm test`) تسقطان بشلّالٍ من
  `Unknown column`: مثلاً `shifts.varianceReasonCode`، `customers.waConsent`، `products.isConsignment` —
  **كلّها غير متعلّقة بالكود المُختبَر**.
- **CI أخضر، المحلّي أحمر:** الحزمة تمرّ في CI فقط، ولا تمرّ محلّياً أبداً. كلّ جلسة تشغّل الاختبارات
  محلّياً تصطدم بـ«مطاردة أعمدة ناقصة» (whack-a-mole).

## ٢. الجذر

قاعدة الاختبار المحلّية `erp_test` على حاوية `erp-test-db` (‏`127.0.0.1:3310`، **MySQL 8.4.9**) تتجمّد
خلف مخطّط `main`، لأنّ `pnpm db:push` (drizzle-kit push) لا يستطيع بناء/مزامنة المخطّط على 8.4.9:

1. **قاعدة فارغة طازجة** ⇒ كان يفشل بـ
   `ER_TOO_LONG_IDENT: Identifier name 'invoiceItemBundleComponents_componentVariantId_productVariants_id_fk' is too long`
   (٦٨ محرفاً > حدّ MySQL ٦٤). هذا الاسم **يولّده drizzle-kit تلقائياً** من `{table}_{col}_{refTable}_{refCol}_fk`
   للمفتاح الأجنبيّ المُعرَّف inline في `drizzle/schema.ts`. **أُصلح** بإعطاء المفتاحين أسماءً صريحةً قصيرة
   (`fk_iibc_item` / `fk_iibc_component`) تطابق migration `0060` — راجع `invoiceItemBundleComponents` في `schema.ts`.
2. **push تزايُديّ على `erp_test` قائمة** ⇒ يفشل بـ
   `ER_DROP_INDEX_FK: Cannot drop index 'PRIMARY': needed in a foreign key constraint` على `pushDailyClaim`
   (drizzle-kit يحاول مصالحة انجرافٍ لا يقدر عليه). **لا علاج له** غير البدء من قاعدة فارغة.

**لماذا CI يمرّ:** CI يستعمل **MySQL 8.0** (راجع `.github/workflows/ci.yml`) على `erp_test` **طازجة**.
الفرق بين 8.0 و8.4 في إنفاذ حدّ اسم المفتاح الأجنبيّ كان يُخفي العلّة الأولى؛ الأسماء الصريحة القصيرة
تُغلقها على **كلّ** إصدارات MySQL 8.x (والمسار الطازج يتفادى العلّة الثانية أصلاً).

> بندٌ ١ عولج في `schema.ts` نفسه، فـ`db:push` الطازج بات ينجح على 8.4.9 كما على 8.0. بندٌ ٢ يتفاداه
> مسار «الطازج دائماً» أدناه.

## ٣. الحلّ: `pnpm test:db:init`

سكريبت [`scripts/init-test-db.mjs`](../scripts/init-test-db.mjs) يعيد بناء قاعدة الاختبار **طازجةً**
بنفس خطوات CI بالضبط (لا push تزايُديّ أبداً):

1. **إسقاط وإعادة إنشاء** القاعدة فارغةً (utf8mb4) — يمحو الانجراف نهائياً ⇒ لا مصالحة ⇒ لا `ER_DROP_INDEX_FK`.
2. `pnpm db:push` — يبني المخطّط من `drizzle/schema.ts` (ينجح على فارغٍ بعد إصلاح اسم FK).
3. `node scripts/ci-apply-extra-migrations.mjs` — يطبّق ما لا يمثّله drizzle-kit (أعمدة `GENERATED`،
   قيود `CHECK`، فهارس مُغطّية…).
4. **(اختياريّ)** تهيئة قاعدة التحكّم لتعدّد الشركات — تُنفَّذ فقط إن ضُبط `TEST_CONTROL_DATABASE_URL`.

### الاستعمال

```bash
# القاعدة الافتراضية erp_test على 3310 (نفس اشتقاق vitest.config.ts):
pnpm test:db:init
pnpm test

# قاعدة شريحة/جلسة مخصّصة: صدّر المتغيّر كي يسري على الأمرين معاً (init ثمّ test) — لو
# قُيّد بالسطر الأوّل فقط، لعاد `pnpm test` إلى .env/erp_test فبطلت العزلة:
export TEST_DATABASE_URL=mysql://root:pw@127.0.0.1:3310/erp_myslice_test
pnpm test:db:init
pnpm test
```

### متى تشغّله

- **مرّةً بعد كلّ تغيير في المخطّط** (`drizzle/schema.ts` أو أيّ هجرة جديدة) قبل تشغيل الحزمة محلّياً.
- عند أوّل ظهورٍ لأخطاء `Unknown column` غير المتعلّقة بالكود.
- بعد `git pull` يجلب هجراتٍ/تغييرات مخطّط من `main`.

## ٤. حرّاس السلامة (خطّ أحمر: مرآة الإنتاج)

السكريبت **يُسقط ويعيد إنشاء** القاعدة، فيرفض قبل أيّ فعلٍ:

| الشرط | السبب |
|------|------|
| مضيف غير محلّي (خارج `localhost`/`127.0.0.1`/`::1`) | لا يمسّ قاعدة بعيدة أبداً |
| المنفذ `3306` | مرآة الإنتاج المحلّية `erp-mysql-prod` — خطّ أحمر (CLAUDE.md). تجاوز واعٍ فقط: `ALLOW_PORT_3306=1` |
| اسم قاعدة بلا «`test`» | كي لا يُسقط `erp` (الإنتاج) أو قاعدة تطويرٍ بالخطأ |

> صندوق الاختبار المخصّص هو `erp-test-db@3310`. **لا** تستعمل `erp-mysql-prod@3306` (المرآة) لأيّ شيء.

## ٥. بدائل مؤجَّلة

- **مواءمة الحاوية المحلّية مع MySQL 8.0** (لمطابقة CI حرفياً) ممكنةٌ لكنها غير ضرورية بعد إصلاح اسم FK:
  المسار الطازج أعلاه يعمل على 8.4.9 و8.0 معاً. أُبقيت الحاوية على `mysql:8` (=8.4.x) بلا تغيير.
- **مواءمة CI مع 8.4** (رفع `image: mysql:8.0` إلى `mysql:8.4`) خيارٌ لاحقٌ لكشف علل 8.4 مبكراً في CI؛
  ليس مطلوباً الآن لأنّ إصلاح اسم FK يجعل المخطّط متوافقاً مع الإصدارين.
