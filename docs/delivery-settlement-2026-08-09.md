# منظومة تسوية التوصيل — تشخيص وإصلاح وحوكمة (٩/٨/٢٠٢٦)

> **بلاغ المالك:** «مشكلة في منظومة التوصيل مالياً ونقدياً وتحاسباً؛ فواتير التوصيل لا تظهر في جدول
> فواتير المندوب/الشركة؛ لا تمييز بصري في شاشة فواتير المبيعات؛ تحاسب المندوب والشركة مبهم» —
> بمبدأ «لا فلس يضيع ولا تعقيد».
>
> **المنهج:** استكشاف ٥ كشّافين متوازين + ٥ عدسات عدائية على مسارات المال (~٣٠ ملاحظة مؤكَّدة
> بالكود) ⇒ إصلاح الحواصر + بناء الرؤية ⇒ ١٣ اختبار حوكمة جديد + مراجعة عدائية على الـdiff
> + تحقق بصري حي كامل.

## ١. النموذج المعتمد (النمط العالمي المبسَّط)

دورة COD القياسية في شركات التوصيل — أربع محطات لكل دينار:

```
إسناد (dispatch)            توريد (remittance)
فاتورة → إرسالية CN-…   →   المندوب يسلّم النقد: كل إرسالية بسطر،
عهدة المندوب += COD          النقد المعدود = الصافي حتماً،
                             الفاتورة تُقيَّد وذمّة العميل تُبرَّأ
        ↓                            ↓
كشف الجهة (statement)   ←   الاستثناءات المحكومة:
مدين/دائن برصيد جارٍ         • إرجاع بضاعة   → returnConsignment (عكس كامل)
+ سجل توريدات DR-…           • عجز إرسالية    → شطب موجَّه (يقفلها ويقيّد فاتورتها)
                             • عجز سائب       → تسوية حرّة (محصورة بالسائب)
                             • نقد عاد بعد شطب → استرداد (يعكس الخسارة)
```

**الثوابت المحروسة:** عهدة الجهة = Σ متبقّي إرسالياتها المفتوحة + العجوزات السائبة ·
Σ(DELIVERY_FEE_HELD) لكل مستند = 0 عند اكتمال الدورة · لا بابين لتحصيل نفس الفاتورة ·
لا عهدة مزدوجة لنفس النقد عبر قناتي المتجر والاستقبال.

## ٢. الحواصر المالية التي أُغلقت (كلها مؤكَّدة بالكود قبل الإصلاح)

| # | الثغرة | الأثر قبل الإصلاح | الإصلاح |
|---|--------|--------------------|---------|
| ١ | `sales.pay` بلا حارس «بالطريق مع المندوب» | تسديد كاونتري لفاتورة بيد مندوب ⇒ عهدة شبح لا تُغلق إلا بشطب يزوّر خسارة | نفس حارس الاستقبال داخل معاملة الدفع (guards.ts) |
| ٢ | «تسوية» المبلغ الحرّ تبتلع عهدة الإرساليات | العهدة تصفَّر والفاتورة تبقى معلّقة للأبد وكشف العميل يطالبه بما دفعه | قصرها على العهدة السائبة (balance − Σ متبقّي الإرساليات المفتوحة) |
| ٣ | الشطب لا يقفل الإرسالية (WRITTEN_OFF ميتة) | إرسالية زومبي تقبل توريداً لاحقاً يقلب الرصيد سالباً وخسارة الشطب تبقى | شطب موجَّه بإرسالية: يقفلها + يقيّد الفاتورة + يُبرّئ ذمّة العميل |
| ٤ | نقد يعود بعد الشطب بلا أي مسار | إمّا يُردّ للمندوب أو يدخل الدرج بلا قيد فيكسر إغلاق الوردية | `recoverWriteOff`: عكس شطب + توريد + إيصال درج (صيغة المطابقة تبقى متوازنة) |
| ٥ | سطر توريد صفري يقلب DISPATCHED إلى PARTIAL | «حُصِّل جزئياً» كاذبة تقفل باب `returnConsignment` نهائياً | الأسطر الصفرية تُستثنى — غير المحصَّل يبقى بالطريق |
| ٦ | توريد إرسالية COUNTER قديمة يقيّد التبرئة **موجبة** | Σ(FEE_HELD) = ضعف الأجرة بدل صفر — التزام وهمي يتضخم | الإشارة سالبة (مرآة مساري الإرسال حرفياً) |
| ٧ | أمانة COUNTER تُبرَّأ بأجرة الإرسال لا بالمقبوض | فرق الأمانة (زبون دفع ٥٠٠٠ وأجرة ٢٠٠٠) يعلق في الدرج للأبد | مساواة إلزامية أمانة=أجرة في مساري الإرسال + فحص إيصالات القبض الفعلية (WO) |
| ٨ | التقاط الأمانة غير محروس خادمياً | أمانة يتيمة عبر API (بلا توصيل COUNTER) أو بمبلغ يفيض عن الأجرة | حارسا وجود التوصيل COUNTER + المساواة في `checkoutReception` |
| ٩ | ازدواج عهدة عبر القناتين (فاتورة ONLINE) | `dispatchInvoice` ثم تأكيد المندوب = عهدة مضاعفة بمفتاحي dedupe مختلفين | رفض ONLINE في dispatchInvoice + رفض إرسالية قائمة في confirmCourierDelivery |
| ١٠ | `floatLimit` غير مفروض على مسار المتجر | مندوب متجر يراكم نقداً بلا حدّ | فحص السقف عند `dispatchOnlineOrder` (البوابة الوقائية قبل خروج البضاعة) |
| ١١ | تغيير فرع جهة عليها إرساليات مفتوحة | حارسا الفرع يتناقضان ⇒ يستحيل توريدها للأبد | رفض تغيير الفرع مع إرساليات مفتوحة + رفض التعطيل معها |
| ١٢ | idempotency الشطب بلا payloadHash + بلا فحص فرع | نفس المفتاح بمبلغ مختلف = «نجاح» صامت بلا تطبيق؛ وخسارة على فرع خاطئ | payloadHash (CONFLICT) + اتساق فرع الجهة |
| ١٣ | كشف حساب العميل لا يرى دفعات توريد المندوب | «كشف يطالب من سدّد» — دفعة التوريد مربوطة بإيصال مجمَّع خارج فلتر الكشف | توسيع بصمة codPay: قيد PAYMENT_IN بلا إيصالٍ مربوطٍ بفاتورة (المتجر + التوريد معاً) |
| ١٤ | شاشة التسوية تحسب الأجور بخلاف الخادم | صافٍ لا يطابق العدّ أبداً لإرساليات COURIER/المصروفة سلفاً = **طريق مسدود** | مرآة `feeStillOwed` حرفياً + وسم «يقبضها المندوب/صُرفت سلفاً — لا تُخصم» |

## ٣. الرؤية التي بُنيت (مطالب المالك الثلاثة الأخرى)

- **شاشة فواتير المبيعات:** عمود «التوصيل» (شارة حالة + اسم الجهة + رقم الإرسالية) + فلتر
  «التوصيل» (بيد المندوب/سُلِّمت/أُرجعت/الكل/بلا) + منتقي «جهة التوصيل» + أعمدة التصدير والنسخ.
  الجذر كان خادمياً: `sales.list` صار يعمل join على الإرسالية (uq يضمن صفاً واحداً — لا تضاعف).
- **تفاصيل الفاتورة:** سطر «إرسالية CN-… — بالطريق — الجهة» برابط عميق لكشف الجهة.
- **لوحة تفاصيل الجهة** (من شاشة الجهات أو الرابط العميق): ٤ تبويبات —
  «الإرساليات والفواتير» (endpoint كان موجوداً وغير مستهلَك)، «سجل التوريدات» (endpoint جديد
  `delivery.remittances` — كان أثر التوريد إيصالاً حرارياً يُطبع مرة واحدة)، «كشف الحساب» حيّ
  بمدين/دائن ورصيد جارٍ والمرجع = **رقم الفاتورة الفعلي** (كان regex على نص الملاحظات) ويشمل
  أمانات الأجرة (كانت تُسقَط صامتاً) وبجمع Decimal (كان Number عائماً)، «بيانات الجهة» (تعديل +
  **سقف العهدة صار قابلاً للضبط** — كان حارساً ميتاً بلا شاشة إدخال + استرداد عجز مشطوب).
- **شاشة التسوية:** عمود الفاتورة بروابط (المندوب يحمل نسخ INV-…).
- **التنقل:** «التوصيل» في قائمة الكاشير المركّزة (منفّذ التوريد الطبيعي كان بلا مدخل مرئي).

## ٤.١ المراجعة العدائية على الشريحة نفسها (٣ عدسات، ١٠/٨) — أُصلحت كلها قبل الدمج

- **(عالية)** الشطب الموجَّه كان بلا «الحزام الثاني»: قيدُ الفاتورة/ذمّة العميل/الخسارة صار
  مسقوفاً بمتبقّي الفاتورة **الحيّ** (مرآة التوريد حرفياً)، والفائضُ عهدةٌ وهمية تُصفّى بلا
  خسارة (G12) — وجذرُها أُغلق: `dispatchInvoice` صار يطرح `returnedTotal` من codAmount (G13).
- استرداد العجز المشطوب صار محصوراً **بفرع الشطب الأصلي** (عكس الخسارة يقع حيث وقعت — G14)،
  ومفتاح idempotency في الواجهة يتجدّد بعد كل نجاح (دفعتان متساويتان كانتا تُبتلعان replay).
- كشف الجهة صار يجمع **ساقَي** أمانة الأجرة (القبض يُكتب قبل معرفة الجهة بلا partyId —
  فلترةُ الجهة وحدها كانت تُظهر «أمانات معلّقة» سالبة كاذبة).
- حارس ازدواج العهدة في تأكيد المندوب قُصر على الإرسالية **المفتوحة** (المغلقة لا خطر منها،
  ورفضها كان يقفل ختم DELIVERED على طلبٍ سُلِّم فعلاً).
- الكشف المطبوع بفترة مفلترة يُختم برصيد الفترة لا بالرصيد الحيّ + يحمل الفترة في ترويسته.
- «العجز» في حوار التسوية صار على الأسطر المُدرَجة وحدها (مطابقاً للإيصال والسجل) مع سطر
  «X إرسالية تبقى بالطريق»؛ `retryOnDeadlock` على الإرجاع/الشطب (طوبولوجيا أقفال متعاكسة
  قائمة تاريخياً)؛ تحقق تواريخ `remittances` بصيغة YYYY-MM-DD؛ لون «شُطبت» موحَّد أحمر؛
  لوحة الاسترداد على مرآة بوّابة الوحدة (`moduleAccessAllowed`) لا قائمة أدوار خام.

## ٥. المتبقّي — يحتاج قرارات مالك (لم يُنفَّذ عمداً)

1. **أجرة شحن المتجر الإلكتروني إيرادٌ كامل في قيد SALE** (تدخل هامش المتجر **ووعاء عمولة**
   الموظف المُرسِل) بينما أجرة الاستقبال تمريرٌ لا إيراد — تناقض دلالي بين القناتين، وتعويض
   مندوب المتجر خارج الدفاتر كلياً. التوحيد قرار سياسة تسعير/محاسبة.
2. **توحيد قناة المتجر في نموذج الإرساليات** (اليوم: المتجر يرفع العهدة عند تأكيد المندوب
   والاستقبال عند الإرسال ⇒ كشف الجهة يخلط توقيتين ولا قراءة موحّدة لـ«ما بيد المندوب الآن»).
   إعادة هيكلة أعمق — تعمل المنظومتان صحيحتين منفصلتين حالياً.
3. **بند خصوم في الميزانية لأمانات الأجرة المعلّقة** (نافذة قصيرة عادة؛ Σ معروضة الآن في كشف
   الجهة) + **سطر إفصاح توصيل في Z-report** + **كاشف anomalyWatch لتقادم العهدة/تكرار العجز**
   + **تقرير أعمار إرساليات مركزي** — تحسينات تقارير مقترحة بالأولوية هذه.
4. تقرير «أداء المناديب» يقرأ طلبات المتجر فقط — ضم إرساليات الاستقبال إليه.
