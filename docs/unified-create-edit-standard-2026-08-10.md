# معيار الإنشاء/التعديل الموحَّد — كتيّب «فريق بناء الشاشات»

**التاريخ:** ١٠ أغسطس ٢٠٢٦ · **الحالة:** معيارٌ حاكم (مُلزِم لكل شاشة إدخالٍ جديدة أو مُعدَّلة).
**الغاية:** أن يرى الموظّف المخوّل **الشاشة نفسها** عند التعديل التي ألِفها عند الإنشاء — لا تخطيطاً غريباً ولا عناصر ناقصة. المبدأ: **التعديل = شاشة الإنشاء نفسها، مُعبّأةً، بحفظٍ مشروط.**

> هذا المعيار مبنيّ على **نمطٍ قائمٍ ومُثبَتٍ في النظام**، لا اختراعٍ جديد: `QuotationNew` تخدم `/quotations/new` و`/quotations/:id/edit` من مكوّنٍ واحد؛ وكذلك `EmployeeNew` للموظفين و`RoleEdit` للأدوار. نُقنّن هذا النمط ونعمّمه.

---

## ١. النمط الحاكم (القالب الذهبيّ — مرجعه `QuotationNew.tsx`)

**مكوّنٌ واحد يخدم الوضعين** عبر علَم `isEdit` مشتقٍّ من مُعامل المسار:

```
const editId = useRoute(".../:id/edit")…;
const isEdit = Number.isInteger(editId) && Number(editId) > 0;

// تحميل الموجود عند التعديل فقط:
const editQuery = trpc.X.get.useQuery({ id }, { enabled: isEdit });

// تعبئةٌ مرّةً واحدة (ref يمنع الكتابة فوق تعديلات المستخدم عند إعادة الجلب):
useEffect(() => { if (isEdit && data && !hydratedRef.current) { …hydrate…; hydratedRef.current = true; } }, [data]);

// حفظٌ مشروط بنفس الواجهة:
const create = trpc.X.create.useMutation(...);
const update = trpc.X.update.useMutation(...);
function submit() { isEdit ? update.mutate({ id, ...editable }) : create.mutate(payload); }

// حالات التحميل/الخطأ للتعديل فقط:
if (isEdit && editQuery.isLoading) return <LoadingState/>;
if (isEdit && !editQuery.data)   return <ErrorState/>;
```

**القاعدة الصلبة:** الجسم المرئيّ (البطاقات/الحقول/الترتيب) **واحدٌ لا يتفرّع** بين الوضعين. الاختلاف يكون في **البيانات والسلوك** لا في **الشكل**.

### البديل المقبول (توأمةٌ لا اندماج)
حين يصعب دمج مكوّنٍ واحد (شاشة إنشاء معقّدة قائمة نُريد عدم لمسها)، يُقبل **مكوّن جسمٍ مشترك** (`XxxFormBody`) يعرضه كلٌّ من `XxxNew` و`XxxEdit` بنفس الـJSX، ويوصلان بياناتهما وحفظهما حوله. **الممنوع:** نسخ الـJSX في ملفّين (كما في `SimpleProductForm`/`SimpleProductEditForm`) — مصدرُ الانحراف المستقبليّ.

## ٢. الفروق المشروعة للتعديل (تُسمح صراحةً — ليست خرقاً للتوحيد)

التوحيد **بصريّ وبنيويّ**، لا يعني تطابقاً أعمى. الفروق التالية **مشروعةٌ ومتوقَّعة** في وضع التعديل:

| الفرق | لماذا | مثال قائم |
|---|---|---|
| **حقول قراءة فقط** | المخزون يُدار عبر الجرد/الحركات لا الإدخال المباشر | `SimpleProductEditForm`: الرصيد الحالي عرضٌ فقط بدل إدخالٍ افتتاحيّ |
| **حقول غير قابلة للتغيير** | تغييرها بعد الإنشاء يستلزم عكس حركةٍ أو يكسر تكاملاً | وحدة الأساس، SKU إلزاميّ (لا مولَّد)، وسم الأمانة مقفولٌ عند مخزونٍ غير صفري |
| **بطاقات خاصّة بالتعديل** | معلوماتٌ لا تُوجد إلا بعد الإنشاء | بطاقة الملخّص (المعرّف/الرصيد/الحالة)، QR، تفعيل/تعطيل، «آخر شراء» |
| **موارد فرعية خادمية** | مسار التعديل قد لا يحمل المورد الفرعيّ في حمولته | بدائل الباركود: محلّية عند الإنشاء، خادمية عند التعديل |
| **حارس التعديل غير المحفوظ** | التعديل يبدأ من بياناتٍ محمّلة ⇒ يلزم كشف «تغيّرٍ حقيقيّ» بلقطةِ أساس | `CustomerEdit`/`SimpleProductEditForm`: `baseline`/`isDirty` |
| **سلوك ما بعد الحفظ** | الإنشاء يغادر؛ التعديل يبقى ويُعيد التعبئة | الإنشاء ⇐ `navigate`؛ التعديل ⇐ `notify` + إعادة تحميل |

**قاعدة عامّة للحقول المحجوبة بالصلاحية:** حين يحجب `get` قيمةً عن غير المخوّل (مثل `creditLimit`)، أرسِل `undefined` عند التعديل **كي لا تُطمَس القيمة المخزَّنة** بقيمةٍ محجوبة (نمط `CustomerEdit`).

## ٣. الكيانات المالية = تصحيحٌ موثَّق لا تعديلٌ حرّ (خطٌّ أحمر)

الفاتورة المُثبَّتة تحرّك الدفتر (قيود SALE/COGS) والمخزون والذمم. **لا تُعدَّل بحرية أبداً.** «تعديلها» يُبنى كـ**تصحيحٍ موثَّق**:
- شاشة التصحيح تبدو كشاشة البيع المألوفة (نفس تحرير البنود) — يُطبَّق المعيار البصريّ أعلاه.
- لكن الحفظ = عملية عكسٍ وإعادة ترحيلٍ متّسقة داخل معاملةٍ واحدة (يوازن الدفتر، يعكس/يعيد COGS، يضبط الذمم)، بأثر تدقيق، محكومةٌ بالصلاحيات، محترمةٌ لأقفال الفترة.
- التصميم التفصيليّ: `docs/invoice-correction-design-2026-08-10.md` (قيد الإعداد، بموافقة المالك قبل أيّ كود).

يسري المبدأ نفسه على كل مستندٍ يحرّك الدفتر (فاتورة شراء مُستلَمة، سند، مسيّر رواتب مُعتمَد…).

## ٤. الصلاحيات

- بوّابة شاشة التعديل تُطابق بوّابة الإنشاء المقابلة **تماماً** (نفس الوحدة والمستوى)، ما لم يقتضِ التصحيح الماليّ رفعها (مثل «التصحيح للمدير فقط» موازاةً للمرتجع).
- الحقول المديرية (سقف الائتمان، الرصيد الافتتاحي، التكلفة) تبقى محجوبةً عن غير المخوّل في الوضعين.

## ٥. خريطة الامتثال (لحظة كتابة المعيار — تحقَّق قبل الاعتماد)

| الكيان | الوضع | ملاحظة |
|---|---|---|
| العروض (Quotation) | ✅ مكوّن واحد | `QuotationNew` يخدم new + :id/edit — **المرجع** |
| الموظفون (Employee) | ✅ مكوّن واحد | `EmployeeNew` يخدم new + :id/edit |
| الأدوار (Role) | ✅ مكوّن واحد | `RoleEdit` يخدم new + :id/edit |
| العملاء (Customer) | ✅ توأمة | `CustomerEdit` «موحَّد على نمط الإضافة» — فروقه مشروعة |
| الموردون (Supplier) | ✅ توأمة | `SupplierEdit` «موحَّد على نمط الإضافة» |
| الأصول (Asset) | ✅ متقارب | حجمان متطابقان تقريباً |
| المنتج — متغيّرات | ✅ مشترك | الإنشاء والتعديل يتشاركان `VariantsTable` |
| المنتج — بسيط | 🟡 توأمٌ بصريّ، **كودٌ مكرّر** | `SimpleProductForm`/`SimpleProductEditForm` متطابقان بصرياً؛ **تكرارٌ يُخاطر بانحراف** (ديْن صيانة — لا ألم بصريّ. إعادة الهيكلة مؤجَّلة لخطورتها على كودٍ ماليّ حسّاس بلا مكسبٍ للمستخدم) |
| **الفاتورة** | 🔴 **فجوة** | `/invoices/:id` عرضٌ فقط؛ التعديل = `sales.correct` محدود/مرتجع ⇒ **الشريحة الرائدة (تصحيح موثَّق)** |
| أوامر الشغل | 🟠 حوار | التعديل حوارٌ مختصر (أُضيف ٩/٨) مختلفٌ عن تدفّق الاستقبال الغنيّ ⇒ مرشّح لاحق |
| المشتريات | 🟠 لا تعديل | `/purchases/:id/receive` فقط؛ لا `/edit` |

**الخلاصة:** شاشات التعديل *المخصّصة* في النظام مُوحَّدةٌ في معظمها (خبرٌ سارّ). **الألم الحقيقيّ يتركّز في الكيانات ذات تدفّق الإنشاء الغنيّ بلا تعديلٍ مماثل** — الفواتير أولاً، ثم أوامر الشغل والمشتريات.

## ٦. قائمة تحقّق «فريق بناء الشاشات» (لكل شاشة إنشاء/تعديل جديدة)

- [ ] مكوّنٌ واحد (أو جسمٌ مشترك) يخدم الوضعين — لا نسخ JSX.
- [ ] `isEdit` من المسار؛ `get` مُفعَّلٌ عند التعديل فقط؛ تعبئةٌ مرّةً واحدة بـref.
- [ ] الجسم المرئيّ لا يتفرّع بين الوضعين؛ الفروق في البيانات/السلوك فقط (§٢).
- [ ] حقول القراءة-فقط وغير القابلة للتغيير مُعلَّمةٌ بوضوح.
- [ ] حارس تعديلٍ غير محفوظ (لقطة أساس) + Ctrl+S/Esc.
- [ ] الحقول المحجوبة بالصلاحية تُرسَل `undefined` عند التعديل (لا طمس).
- [ ] بوّابة الصلاحية تُطابق الإنشاء (أو أعلى للتصحيح الماليّ).
- [ ] كيانٌ ماليّ؟ ⇒ تصحيحٌ موثَّق لا تعديلٌ حرّ (§٣).
- [ ] **تحقّقٌ بصريّ حيّ أنّ شاشة الإنشاء لم تتغيّر بكسلٍ واحد** بعد أي استخراجٍ مشترك.
- [ ] فحص `pnpm check` + الحرّاس (colors/form-inputs/emoji) + اختبار.

## ٧. الحرّاس (منع الانحراف مستقبلاً)

- استعمل توكنز التصميم الدلالية دائماً (`text-money-*`/`text-stock-*`/`text-[var(--sem-info)]`) — `check:colors` يرفض الألوان الخام.
- حقول الهاتف: `IntlPhoneInput`؛ حقول المال: `MoneyInput` — `check:form-inputs` يفرضهما.
- (مقترح مستقبليّ) حارسٌ يرصد أزواج `XxxNew`/`XxxEdit` التي تكرّر JSX بدل جسمٍ مشترك.
