# تصحيح ملاحظات اعتماد PR1595

هذه لقطة إعداد الرأس البديل؛ نتيجة الاعتماد النهائية تُسجّل في طلب الدمج على رأسه الحالي.

## اعتماد الحاويات المحلية

كشف GitGuardian ثلاثة مواضع لاعتماد Docker محلي فعلي في مساعدات التدقيق. إدراج هذه القيم في المصدر خطأ، حتى مع اقتصار المنافذ على loopback. لم تكن القيم اعتماد الإنتاج، لكن حاوية التدقيق المحلية تحتوي اللقطة المصرح بنسخها، لذا لم نكتفِ باعتبارها أمثلة.

أزيلت القيم من المساعدات الأربع، وأصبحت تقرأ ملف اعتماد خارج Git عبر AUDIT_LOCAL_DB_ACCESS_FILE. الملف محمي بقائمة وصول Windows صريحة للمستخدم الحالي وSYSTEM/Administrators، ويثبت الحاوية والمنفذ وUUID والمخطط. جرى تدوير اعتماد root للحاويتين المملوكتين على33318 و33320، ونجح الاتصال الجديد ورُفض القديم. بقي event_scheduler=OFF، وطابقت بصمة الدَمب وعدادات اللقطة الأصلية القيم المحفوظة. لم تُكتب سجلات أعمال أو أرصدة.

حُفظت نسخة Git bundle محلية قبل تنقية تاريخ فرع الإصلاحات. الرأس البديل لا يرث التزامَي الفرع اللذين احتويا القيم؛ يبقى main محفوظاً. لا توجد استثناءات لحارس الأسرار أو قواعد تجاهل أضيفت لتجاوز الملاحظة. يلزم نجاح الحارس على الرأس البديل قبل اعتماد الإصدار.

MYSQL_ROOT_PASSWORD في إعداد الحاوية يظل قيمة التهيئة القديمة غير الفعالة لقاعدة البيانات القائمة؛ الاعتماد المحمي هو مرجع الاتصال الحالي. يجب تجهيز أي حاوية جديدة باعتماد جديد، ولا تعاد قيمة التهيئة القديمة. لا يوجد healthcheck يعتمد القيمة القديمة في حاوية اللقطة.

## عميل النسخ مع MySQL 8.0

المراجعة الآلية كشفت أن --init-command غير موجود في mysqldump8.0، بينما تكوين المشروع يعتمد خادم8.0. نجاح التجربة السابقة بعميل8.4 لا يثبت توافق هذا المسار. أُصلح الاختيار بفحص قدرة العميل: القادر يبقى كما هو؛ وإلا يستعمل هدف Docker المتحقق عميلاً8.4.9 مثبتاً بالـdigest داخل حاوية مؤقتة غير مميزة تشارك شبكة الخادم فقط. لا تُحمّل حجم بياناته، ولا تنشر منافذ، ولا تحفظ SQL في Docker logs.

التجهيز الصريح يسبق نسخة أمان النشر؛ النسخ المعتادة تستعمل --pull=never. يبقى اختبار UUID داخل اتصال التفريغ وإعادة اتصاله، وينفذ التنظيف بعد تحقق ملكية الحاوية. لا ترقية لخادم قاعدة البيانات. فحص مستقل لم يبقِ اعتراضاً مادياًP1/P2 ضمن هذا النطاق. اختبارات Node وتجهيز العميل المخزّن دون شبكة نجحت؛ إثبات التفريغ وroundtrip الفعليين على8.0 ينتظر خطوة CI المضافة إلى الشارد1، ولا يُسجل نجاحاً قبل تنفيذها.

## إخفاقا تجهيز الاختبارات

تحقق القائد بعد استلام تصحيح النسخ:37اختبارNode ناجح وحالة التكامل الفعلية على8.0 متجاوزة صراحةً محلياً، واختبار عقد النشر ناجح. اجتازت ضوابط هدف التدقيق قراءةً فقط: الملكية وUUID وتعطيل المجدول ورفضUUIDخاطئ أو مخطط اللقطة أو ملف اعتماد مفقود. هذه نتائج محلية؛ اعتمادCI للرأس البديل ما زال مستقلاً.

الشارد3 توقف في خمس حالات عهدة لأن الفاعل الإداري لم يكن مزروعاً في users؛ زُرع حساب فعّال حقيقي، مع بقاء التأكيدات المالية. الشارد8 استعمل أربع توقعات عددية لرصيد أصبح DECIMAL؛ صارت نصوصاً دقيقة27.00/24.00/24.00/30.00 مع حفظ رفض إلغاء الذات والرصيد بعده. الملفان اجتازا16حالة فعلية على قاعدة اصطناعية منفصلة عن اللقطة. لم تخفف الحراس أو الحسابات أو خط أساس الأنواع.

## تنبيه اعتماديات خارج سجل37

توجد ثلاثة تنبيهات منخفضة لنفس [تنبيه deepmerge](https://github.com/advisories/GHSA-gcqx-w48m-w2h4) في قفل الجذر وقفلَي Expo. يصف المصدر تسميم prototype للكائن الناتج، ولا يسجل نسخة مصححة حتى المراجعة الحالية. مسار الجذر تبعية تطوير لأدوات PWA؛ التنبيهان الآخران مصنفان runtime في قفلَي التطبيقين. لم ندّع إغلاقهما أو سلامة كل مدخل يصل إليهما؛ يتطلبان متابعة مستقلة، ولا تعني خضرة بوابة audit انعدام التنبيهات المنخفضة.
