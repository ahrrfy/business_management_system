# بروتوكول الفحص الجنائي لوحدات ERP — ERPM-Forensic Protocol v1.0
## الدليل المؤسسي والتشغيلي لنظام إدارة أعمال «الرؤية العربية»

> **الأنظمة غير المفحوصة جنائياً تحتوي دائماً على ثغرات غير مرئية.**  
> هذا البروتوكول يفكك النظام البرمجي والمالي إلى مستويات ذرية — كل فحص = سؤال محدد واحد، تأكيد واحد، نتيجة متوقعة واحدة، وحكم قاطع: Pass / Warning / Fail / Critical.

---

## ١. المبدأ الأساسي: الفحص الذري (Atomic Inspection Principle)

لا يُقبل في التدقيق الجنائي أي حكم انطباعي أو عام مثل «الوحدة تعمل بشكل جيد» أو «تم فحص النماذج». التدقيق يقوم على البناء الذري:

```
لكل وحدة Module:
  لكل طبقة Layer (قاعدة البيانات ──▶ الخدمات ──▶ الراوترات ──▶ الواجهة):
    لكل نقطة تفتيش Checkpoint:
      → سؤال محدد واحد لا يقبل التأويل
      → معيار قبول صريح ومقاس برمجياً أو سلوكياً
      → حكم قاطع:
          ✅ Pass     : استيفاء كامل للمعيار دون أي ملاحظة
          ⚠️ Warning  : انحراف لا يوقف العمل لكنه يُخل بالمعايير أو يراكم ديناً تقنياً
          ❌ Fail     : خلل وظيفي أو خرق لمنطق الأعمال
          🔴 Critical : خسارة بيانات / أثر مالي كاذب / ثغرة أمنية / خرق ذرية
      → توثيق فوري مدعوم بالدليل الجنائي (سجل كود، استعلام، أو مسار استدعاء)
```

1. **أولاً — المستوى 3: سلامة البيانات والمعاملات الذرية** 🔴 (خسائر مالية مباشرة / تضارب مخزني أو نقدي).

## ٣. الهيكل التنفيذي: المستويات التسعة للبروتوكول

### المستوى 0 — الإعداد قبل الفحص (Pre-Inspection Setup)
**الهدف:** بناء بيئة فحص معزولة تماماً تمنع تلوث بيئة الإنتاج وتضمن إمكانية إعادة إنتاج أي نتيجة.

| الإجراء | المتطلب الفني في نظام الرؤية العربية | المخرج |
|---|---|---|
| **ENV Snapshot** | أخذ لقطة كاملة من الكود وقاعدة البيانات (`git rev-parse HEAD` + نسخة احتياطية من MySQL) | معرّف التزام وقاعدة معزولة |
| **Scope Document** | تحديد الجداول، الخدمات، والراوترات والشاشات المستهدفة بالاسم | ملف `docs/ERPM-SCOPE-<MODULE>.md` |
| **Dependency Map** | رسم خريطة تدفق البيانات بين الوحدة والوحدات المجاورة (المخزن، الخزينة، الدفتر) | مخطط تدفق الاعتمادات والتأثيرات |
| **Test Environment** | عزل قاعدة الاختبار تماماً على المنفذ المخصص (مثل 3310) ومنع لمس منفذ الإنتاج (3306) | خلو السجلات من أي بيانات حية |
| **Baseline Metrics** | تسجيل أداء الاستعلامات وزمن الاستجابة للعمليات الأساسية قبل الفحص | مقياس خط الأساس المرجعي |

### المستوى 1 — الفحص الثابت (Static Analysis)
**الهدف:** اكتشاف العلل البنيوية والمخاطر الصامتة في الشيفرة وقاعدة البيانات دون الحاجة للتشغيل.

#### 1.1 — فحص المخطط وقاعدة البيانات (Schema Audit)
*تُفحص الجداول المرتبطة بالوحدة في `drizzle/schema.ts`:*
- □ **صحة الأنواع:** هل كل حقل مالي معرّف كـ `decimal(15, 2)` (أو `15, 4` لسعر الوحدة الدولاري)؟ (🔴 استخدام `float` أو `double` للأموال يُعد فوراً Critical).
- □ **المفاتيح الأجنبية والقيود:** هل المفاتيح الأجنبية `foreignKey` معرّفة صراحة ومربوطة بسياسة حذف واضحة (مثل `onDelete: "restrict"`)؟
- □ **الفهارس الحيوية:** هل حقول البحث والربط الأساسية (`branchId`, `status`, `createdAt`, `sourceId`) مغطاة بفهارس مناسبة؟
- □ **حقول الـ NULL:** هل الحقول التي يعتمد عليها منطق الأعمال معرفة بـ `notNull()` لمنع الانهيار الصامت؟
- □ **معايير التسمية:** هل تتبع الجداول والأعمدة النمط الموحد `camelCase` في Drizzle و`snake_case` أو المسميات المتعاقد عليها في DB؟
- □ **الجداول اليتيمة:** هل توجد جداول من مخلفات إصدارات قديمة لا يستدعيها أي ملف كود حالي؟

#### 1.2 — فحص الكود (Code Review)
- □ **القيم الثابتة (Hardcoded Values):** هل توجد أرقام، أسماء فروع، نسب خصم، أو عملات مكتوبة يدوياً في كود الخدمات أو الشاشات؟ (البديل: التوكنز وقواميس `shared/`).
- □ **التعليقات الصادقة:** هل تعليقات الكود تطابق السلوك الفعلي أم تصف سلوكاً تم تعديله تاريخياً؟
- □ **الكود المعطوب (Dead Code):** هل توجد دوال، إجراءات راوتر، أو مسارات استيراد لا تُستدعى قط؟
- □ **المسؤولية الواحدة (SRP):** هل تفعل الدالة شيئاً واحداً فقط؟ وهل الراوتر معزول عن منطق الأعمال (Validation + Procedure Calling فقط)؟
- □ **معالجة الأخطاء:** هل تُرمى الأخطاء عبر `TRPCError` مصحوبة برسائل مهيكلة عبر `appErrorMessage` من `shared/errors.ts` توضح (ماذا حدث، لماذا، وما العمل)؟

#### 1.3 — فحص الإعدادات والأمان الساكن (Configuration Audit)
- □ **عزل المتغيرات:** هل بيانات الاتصال بقاعدة البيانات ومفاتيح التشفير محصورة في `.env` ومستثناة تماماً من Git؟
- □ **تطابق الإعدادات:** هل إعدادات بيئة التطوير والاختبار مفصولة ولا تتضمن بيانات حقيقية للعملاء؟
- □ **الأسرار المكشوفة:** فحص الكود لمنع وجود كلمات مرور تجريبية، مفاتيح JWT، أو مفاتيح API داخل المستودع.

### المستوى 2 — الفحص الديناميكي والوظيفي (Dynamic Functional Testing)
**الهدف:** اختبار كل عملية بالتشغيل الفعلي بمصفوفة حالات متكاملة.

لكل عملية في الوحدة (إنشاء، تعديل، حذف، اعتماد، إلغاء، استرجاع):
1. **المسار السعيد (Happy Path):**
   - هل تنجح العملية وتعيد النتيجة المتوقعة عند تزويدها بمدخلات صحيحة ومكتملة؟
   - هل تتطابق حالة الواجهة فوراً مع الحالة المسجلة في الخادم؟
2. **اختبار الحدود والقيم الحدية (Boundary Testing):**
   - ماذا يحدث عند إدخال قيمة صفرية (كمية = 0 أو سعر = 0)؟
   - ماذا يحدث عند إدخال قيمة سالبة؟ هل تُرفض ما لم تكن العملية حركة مرتجع صريحة؟
   - ماذا يحدث عند إدخال كمية تتجاوز الرصيد المتاح بالمخزن (إلا في الحالات المصرحة كـ `allowBackorder`)؟
   - ماذا يحدث عند إدخال نصوص أو محارف خاصة في حقول الأرقام والمبالغ؟
3. **المسار السلبي (Negative Testing):**
   - هل تظهر رسالة خطأ مفهومة وواضحة للمستخدم دون عرض تفاصيل تقنية غامضة أو Stack Trace؟
   - هل يظل النظام مستقراً بعد وقوع الخطأ ويمكن متابعة العمل دون إعادة تحميل الصفحة؟
   - هل تبقى قاعدة البيانات متماسكة تماماً دون ترك أي صفوف غير مكتملة بعد عملية فاشلة؟

### المستوى 3 — سلامة البيانات والذرية المالية (Data Integrity Audit) 🔴 [الأولوية الأولى]

> **المبدأ المالي الحاكم للرؤية العربية:** «لا دينار يضيع بصمت أو يُهدر أو يختفي أو ليس له مسار أو تبويب.»

#### 3.1 — تسلسل المعاملات الذرية (Transaction Consistency)
- □ **قفل المعاملة الشامل:** هل تتم كل عملية ذات أثر مالي أو مخزني داخل `withTx(async (tx) => ...)`؟
- □ **الارتداد الكامل (Rollback):** إذا فشل تحديث حركة المخزون، هل يرتد تسجيل الفاتورة وسند القبض تلقائياً؟
- □ **منع الحالة النصفية:** هل يستحيل برمجياً أن ينتهي النظام بحركة مخزنية دون قيد دفتر أو العكس؟
- □ **تأجيل التأثيرات الجانبية:** هل المؤثرات الخارجية (مثل إرسال إشعارات أو طباعة) مؤجلة لما بعد اكتمال المعاملة عبر `enqueuePostCommit` لضمان عدم إطلاقها عند فشل الـ Tx؟

#### 3.2 — سلامة المراجع ومنع الأيتام (Referential Integrity)
- □ هل يمنع النظام حذف عميل أو مورد إذا كانت له فواتير أو حركات مالية مرتبطة؟
- □ هل يمنع حذف منتج أو صنف له رصيد مخزني أو مرتبط بأوامر شغل أو مبيعات قائمة؟
- □ هل يمنع حذف حساب مالي أو خزينة تحتوي على قيود مرحلة؟ (أي إمكانية لحدوث ذلك = 🔴 Critical).

#### 3.3 — مسار التدقيق غير القابل للتلاعب (Audit Trail)
- □ هل تسجل كل حركة: من الفاعل (`userId`, `Actor`)؟ متى نُفذت (بتوقيت الخادم الموحد UTC)؟ وما هي تفاصيل التغيير (`diff`, `payload`)؟
- □ هل يستحيل حذف أو تعديل سجلات `auditLogs` عبر واجهة المستخدم أو الـ API؟
- □ هل الفاعل منسوب بدقة لحسابه الفعلي دون تزييف الهوية عبر الـ Client Payload؟

#### 3.4 — دقة الحسابات المالية (Financial Calculation Accuracy)
- □ هل تُجرى كافة الحسابات المالية باستخدام مكتبة `decimal.js` ومساعدات `money.ts`؟
- □ هل يُحظر تماماً استخدام `parseFloat` أو `Number(...)` على المبالغ المالية؟
- □ هل يتطابق إجمالي الفاتورة دائماً وبلا استثناء مع مجموع بنودها مخصوماً منها الخصم المعتمد ومضافاً إليها الرسوم؟
- □ هل تخضع العمليات بالعملات الأجنبية لدقة المنازل المعتمدة (الدينار: منزلتان، الدولار: 4 منازل لسعر الوحدة)؟

### المستوى 4 — منطق الأعمال والحوكمة (Business Logic Validation) 🔴 [الأولوية الثالثة]

#### 4.1 — مركزية قواعد العمل
- □ **المصدر الوحيد للحقيقة:** هل قواعد العمل مطبقة مركزياً في طبقة الخدمات (`server/services/*`) بدلاً من تشتيتها في واجهة المستخدم؟
- □ **منع التكرار والانجراف:** هل التحقق في الواجهة هو تحسين لتجربة المستخدم فقط بينما الإنفاذ الصارم محمي في الخادم؟
- □ **توحيد القواميس:** هل قواميس الحالات، طرق الدفع، وقنوات البيع مستوردة من حزمة `@shared/` المشتركة؟

#### 4.2 — مسارات وسير العمل (Workflow & State Machine)
- □ **ضبط الانتقالات:** هل حالات المستند (مسودة → معتمد → منفذ → مقفل) محكومة بسجل الانتقالات (`automationRegistry` أو `decisionRegistry`)؟
- □ **فصل المهام (SOD):** هل يُمنع منشئ الطلب أو المستند من اعتماده بنفسه (Maker-Checker) ما لم يكن مالكاً بصلاحية استثنائية صريحة ومسجلة؟
- □ **منع القفز والتخطي:** هل يستحيل نقل المستند من مرحلة ابتدائية إلى مرحلة نهائية متجاوزاً بوابات الاعتماد؟
- □ **المستندات الميتة:** هل يُمنع منعاً باتاً إضافة أي سند قبض أو تعديل على فاتورة أو أمر بحالة ميتة (`CANCELLED`, `RETURNED`, `SUPERSEDED`)؟

### المستوى 5 — الأمن والتحكم بالوصول (Security Audit) 🔴 [الأولوية الثانية]

#### 5.1 — التحكم الصارم في الوصول (RBAC & Branch Scoping)
- □ **بوابات الإجراءات:** هل كل إجراء في الراوتر محمي بإجراء تفويض مناسب (`moduleProcedure`, `branchScopedProcedure`, `adminProcedure`)؟
- □ **عزل الفروع (Branch Isolation):** هل يُمنع موظف فرع معين من الاطلاع على مبيعات أو خزينة فرع آخر ما لم يملك دوراً إدارياً عاماً؟
- □ **عزل سجلات الموظف:** هل يستعلم الموظف العادي عن سجلاته فقط عبر `scopedOwnerId`؟
- □ **منع تصعيد الصلاحيات (Privilege Escalation):** هل يستحيل على مستخدم عادي تمرير `role` أو `branchId` في الحمولة لتجاوز هويته في الجلسة؟

#### 5.2 — فحص المدخلات والثغرات الشائعة
- □ **حقن SQL:** هل كل الاستعلامات تستخدم استعلامات Drizzle المهيكلة أو المعاملات المجهزة (Parameterized Queries) دون دمج نصوص خام غير معقمة؟
- □ **XSS والتعقيم:** هل يتم تعقيم وعرض نصوص المستخدمين بشكل آمن في React دون استخدام `dangerouslySetInnerHTML` على مدخلات غير موثوقة؟
- □ **تقييد الحجم:** هل كافة حقول الإدخال مقيدة بأطوال قصوى منطقية في مخطط Zod؟

#### 5.3 — حماية البيانات الحساسة
- □ هل كلمات المرور مشفرة بخوارزمية `scrypt` أو ما يماثلها بأملاح فريدة، ومستبعدة تماماً من أي استجابة API؟
- □ هل جلسات العمل تعتمد رموز JWT الموقعة عبر `jose` بمدد انتهاء محددة؟

### المستوى 6 — الأداء والكفاءة (Performance Profiling)
- □ **معضلة N+1:** هل تستعلم الخدمات عن العلاقات التابعة عبر استعلامات مجمعة (`inArray`) أو Relational Queries بدلاً من الاستعلام داخل حلقات التكرار؟
- □ **فهارس الأداء:** هل تملك الجداول الكبيرة فهارس على حقول التصفية والفرز الشائعة؟
- □ **التقسيم والتصفح (Pagination):** هل الجداول وشاشات العرض تطبق الترقيم على جانب الخادم لمنع تحميل آلاف السجلات دفعة واحدة؟
- □ **تجمد الواجهة:** هل العمليات الحسابية والتقارير الثقيلة تعمل في الخلفية دون تعطيل استجابة الصفحة؟

---

### المستوى 7 — التكامل بين الوحدات (Integration Testing)
- □ **نقاط التلامس (Touchpoints):** تحديد أثر العملية على الوحدات الشريكة (مثال: بيع POS ← ينقص المخزون ← ينشئ إيصالاً نقدياً ← يدرج قيد دفتر ← يحدّث رصيد الدرج).
- □ **التعامل مع التعثر:** إذا تعثرت وحدة تابعة، هل يرتد التأثير دون ترك بيانات معلقة بين الوحدات؟
- □ **تطابق المفاهيم والكيانات:** هل تعريف العميل أو الحساب المالي متطابق في وحدة المبيعات مع وحدة الحسابات والخزينة؟

---

### المستوى 8 — تجربة المستخدم والوقاية الجنائية (UX/Usability Forensic)
- □ **منع النقر المزدوج (Double-Submit Protection):** هل الأزرار الحساسة (دفع، اعتماد، إلغاء) معطلة أثناء الإرسال (`isPending`) مع مؤشر تحميل؟
- □ **رسائل الإرشاد والخطأ:** هل الرسائل توضح للمستخدم الخطأ الفعلي وكيفية تصحيحه (مثل: «الرصيد المتاح 3 قطع والمطلوب 5») وتتجنب الرسائل العمياء؟
- □ **حوارات التأكيد الصريحة:** هل العمليات الخطرة أو المالية تطلب تأكيداً مخصصاً يوضح الأثر المادي بدقة عبر مكون `<ConfirmDialog>`؟
- □ **اختصارات الحفظ المعتمدة:** هل تدعم النماذج اختصار `Ctrl+S` الموحد وفقاً لحارس `check:save-shortcut-coverage`؟

### المستوى 9 — التوثيق، خارطة التحسين، وبطاقات الخلل (Roadmap & Defect Cards)

#### 9.1 — مصفوفة خطورة الخلل وسرعة المعالجة
| الدرجة | التعريف والأثر | المهلة القصوى للمعالجة |
|---|---|---|
| **🔴 P0 Critical** | فقدان بيانات، خرق للذرية المالية، ثغرة أمنية تسمح بتجاوز الصلاحيات، أو خطأ حسابي في الأموال | فوراً (خلال 24 ساعة) |
| **🟠 P1 High** | خلل وظيفي في مسار رئيسي يوقف عمل الكاشير أو الاعتمادات اليومية | خلال أسبوع |
| **🟡 P2 Medium** | سلوك غير صحيح أو عدم تطابق في الواجهة لا يوقف العمل التجاري وله بديل | خلال شهر |
| **🔵 P3 Low** | تحسين أداء، صقل تجربة المستخدم، أو معالجة دين تقني | خلال دورة ربع سنوية |
| **🟢 P4 Enhancement** | فكرة تحسينية أو تطوير استراتيجي للمسار | جدول التحسينات (Backlog) |

#### 9.2 — هيكل بطاقة الخلل الجنائي (Defect Card)
كل خلل يتم رصده يُوثق في بطاقة معيارية مستقلة:
```markdown
### بطاقة خلل جنائي: [DEF-XXXX]
- **الوحدة:** [اسم الوحدة، مثل: Returns / Sales / Treasury]
- **المستوى:** [المستوى من 1 إلى 8]
- **درجة الخطورة:** [🔴 P0 | 🟠 P1 | 🟡 P2 | 🔵 P3 | 🟢 P4]
```
