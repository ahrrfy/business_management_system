# تشخيص فشل CI الآمن

مسار **CI Failure Diagnostics** يراقب فقط اكتمال سير `CI` و`Native Android CI` و`Security Audit`. عند نتيجة غير ناجحة، ينشئ Issue واحداً لكل رقم تشغيل، يتضمن رابط التشغيل وSHA والفرع والوظائف والخطوات الفاشلة. لا يجلب سجل stdout/stderr لأن السجل قد يحتوي أسراراً أو بيانات حساسة؛ يستخدم البيانات الوصفية من GitHub Actions فقط.

| مسموح                                | محظور صراحةً                                        |
| ------------------------------------ | --------------------------------------------------- |
| قراءة حالة التشغيل والوظائف والخطوات | تشغيل كود الفرع أو checkout له                      |
| إنشاء Issue تشخيصي مكرر الحماية      | إنشاء branch أو commit أو Pull Request              |
| تشغيل يدوي لـ`run_id` محدد           | الدمج أو النشر أو تنفيذ migrations أو استخدام أسرار |

لا يمتلك المسار `contents: write` أو `pull-requests: write` أو `deployments: write`. لذلك لا يمكنه أن يصبح مسار إصلاح أو إطلاق إنتاجي بمجرد إدخال نص في سجلات CI. أي إصلاح فعلي يجب أن ينشأ في PR منفصل، يمر بجميع البوابات الإلزامية، ويأخذ مراجعة بشرية.

لتشخيص تشغيل سابق يدوياً، افتح مسار **CI Failure Diagnostics** في GitHub Actions، اختر **Run workflow**، ثم أدخل رقم التشغيل الفاشل. إذا كان التشغيل ناجحاً أو ملغى فلن يُنشأ Issue.
