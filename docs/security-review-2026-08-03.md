# مراجعة أمنية شاملة — النظام كله + المتجر (٣ أغسطس ٢٠٢٦)

> مراجعة أمنية عدائية من الكود فقط (لا اعتماد على تدقيقات سابقة). سطح المراجعة: طبقة
> المصادقة/الجلسة/CSRF، ٧٤ راوتر tRPC، المتجر العلني (storefront)، مسارات HTTP خارج tRPC
> (webhooks/صور/طباعة/نسخ/وسائط)، التشفير والأسرار، حقن SQL والمدخلات، وعزل تعدّد الشركات.
> المنهج: ٦ محاور بالتوازي + تحقّق شخصي من رأس كل محور بقراءة الكود.

## الخلاصة التنفيذية

**الوضع الأمني قويّ بشكل ملحوظ.** لا ثغرة CRITICAL قابلة للاستغلال في النشر الحالي (أحادي
الشركة). طبقة المصادقة/التفويض ناضجة وتحمل آثار تدقيقات متعدّدة سابقة. **لا حقن SQL، لا ثغرات
تبعيات معروفة، لا XSS في الواجهة، لا أسرار مُسرَّبة، تسعير المتجر خادميّ بالكامل.**

الثغرتان الأخطر (HIGH) كلتاهما في **مسار توفير الشركات** وتتطلّبان تفعيل تعدّد الشركات
(معطَّل حالياً على الإنتاج) — لكنهما تكسران ضمان «أقلّ امتياز» المُعلَن وتستحقّان الإصلاح قبل
أي تفعيل. البقية MEDIUM/LOW معظمها تقوية دفاع عميق.

| الشدّة | العدد |
|--------|-------|
| CRITICAL | 0 |
| HIGH | 2 (كلاهما مسار التوفير، كامنٌ حتى تفعيل تعدّد الشركات) |
| MEDIUM | 9 |
| LOW / دفاع عميق | 15 |

## HIGH

### H1 — منح صلاحيات MySQL بأحرف بدل `_` غير مهرَّبة ⇒ وصول محتمل لقاعدة التحكّم `erp_control`
**الملف:** `scripts/lib/provisionCompany.mjs:62,78`
```js
const dbName = `erp_co_${code.replace(/-/g, "_")}`;          // كود "trol" → erp_co_trol
...
`GRANT ALL PRIVILEGES ON \`${dbName}\`.* TO '${dbUser}'@'%';`
```
في عبارة `GRANT ... ON db.*` يُعامِل MySQL محرفَي `_` و`%` في اسم القاعدة **كأحرف بدل**،
والتنصيص بـbacktick **لا يُلغي** ذلك (سلوك موثَّق — يلزم تهريبها `\_`). اسم القاعدة
`erp_co_<code>` يحوي شرطتين سفليتين غير مهرَّبتين ⇒ المنح فعلياً **نمطٌ** لا اسمٌ حرفيّ.

**الاستغلال (الأثر CRITICAL إن بُلِغ):** شركة تُوفَّر بالرمز `trol` ⇒ `dbName = erp_co_trol`.
مطابقة النمط حرفاً بحرف مع `erp_control` (١١ حرفاً، الشرطة عند الموضع ٧ تطابق `n`):
`e r p [_] c o [_→n] t r o l` = `erp_control`. عندها يملك مستخدم قاعدة تلك الشركة
`ALL PRIVILEGES` على **قاعدة التحكّم** — التي تحوي كلمات مرور قواعد كل الشركات المشفّرة +
هاشات مدراء المنصّة + بيانات اتصال كل شركة. الكتابة عليها = استيلاء كامل على المنصّة.
وبشكل عام، الضمان المُعلَن «المستخدم لا يصل لأي قاعدة أخرى» غير صحيح بنيوياً لأي شركة.

**الإصلاح:** هرِّب أحرف البدل في GRANT: `` ON `erp\_co\_${...}`.* `` (استبدل `_`→`\_` في
نسخة GRANT فقط)، أو استعمل اسم قاعدة/مستخدم بلا `_`. أضِف اختبار تكامل يؤكّد رفض مستخدم
الشركة على `erp_control` وعلى قاعدة شركة أخرى.

### H2 — كلمة مرور جذر MySQL + كلمة مرور قاعدة كل شركة مكشوفتان في `argv` أثناء التوفير
**الملف:** `scripts/lib/provisionCompany.mjs:66-80`
```js
execFileSync("docker", ["exec", opts.dbContainer, "mysql", "-uroot", `-p${opts.rootPw}`, "-e", sql], ...)
// وSQL يحوي: CREATE USER ... IDENTIFIED BY '${dbPassword}'
```
`-p${rootPw}` يضع كلمة مرور الجذر على سطر الأوامر، و`-e ${sql}` يمرّر كلمة مرور قاعدة الشركة
الجديدة كعنصر argv. على خادم مشترك (VPS إنتاج Serj/Odoo)، `ps aux`/`/proc/<pid>/cmdline`
يكشف argv لأي مستخدم محلّي أثناء نافذة التنفيذ. كشف كلمة مرور الجذر = اختراق كامل عبر كل
الشركات.

**الدليل على أنه سهوٌ لا قرار:** المشروع يعالج هذا بالضبط في كل مسار آخر عبر `MYSQL_PWD` —
راجع `scripts/restore.mjs:79-90` (تعليق «BC-04: يُكشَف في ps على خادم مشترك») و
`scripts/backup.mjs:90-91,111,139`. مسار التوفير هو الاستثناء الوحيد المنسيّ.

**الإصلاح:** مرّر كلمة مرور الجذر عبر `docker exec -e MYSQL_PWD` والـSQL عبر stdin
(`mysql` بلا `-e`، `input: sql`) — نفس نمط `restore.mjs`/`backup.mjs`.

## MEDIUM

### M1 — IDOR على وسائط واتساب: أي مستخدم مصادَق يعدّد كل مرفقات محادثات العملاء
**الملف:** `server/routes/waMedia.ts:47-60` + `server/services/whatsapp/mediaService.ts` (`getMediaForServing`)
المسار `GET /api/wa/media/:messageId` يتحقّق من الجلسة فقط (`getUserFromRequest`) **بلا فحص
دور/فرع/وحدة**، و`messageId` عدد صحيح تسلسلي، و`getMediaForServing` يستعلم بالمعرّف فقط بلا
أي شرط ملكية. كاشير أي فرع يعدّ المعرّفات (`/1`, `/2`, …) فيسحب كل وسائط واتساب داخل الشركة
(قد تحوي وثائق هوية/صور خاصة/مستندات دفع). عزل الشركات سليم؛ الثغرة داخل الشركة الواحدة.
**الإصلاح:** قيِّد الوصول بربط الوسائط بفرع المحادثة (branchId) أو بمفتاح صلاحية inbox/whatsapp.

### M2 — تسريب «حصة المودِع» (= التكلفة) لأدوار لا ترى التكلفة عبر `consignments.consignorProducts`
**الملف:** `server/routers/consignmentRouter.ts:61-63` + `server/services/consignment/noteService.ts:483`
الإندبوينت يعيد `share: productVariants.costPrice` **بلا حجب تكلفة**، والمعامل `_branchId`
مُتجاهَل (لا عزل فرعيّ). البوّابة `consignmentReadProcedure` تسمح لأدوار warehouse/purchasing/
auditor — وكلّهم **ليسوا canSeeCost** — بينما `shared/permissions.ts:173` ينصّ صراحةً أن
warehouse «لا يرى الحصة». يناقض التحصين المطبَّق على شقيقَيه `list`/`get` (تدقيق ٢٥/٧).
**الإصلاح:** احجب `share` عبر `canSeeCostForUser(ctx.user)` (كنمط `redactPosCost`) وفعِّل عزل الفرع.

### M3 — تعداد سجلّ طلبات زبون معروف الهاتف عبر `storefront.trackOrder`
**الملف:** `server/routers/storefrontRouter.ts:140` + `server/services/onlineOrderService.ts:329,372`
رقم الطلب متسلسل ومتوقَّع (`ORD-${100000 + orderId}`)، والعامل الثاني الوحيد هو الهاتف
(شبه علني في العراق). `trackOnlineOrder` يعيد الطلب كاملاً (الأصناف، أسعار الوحدة، الكميات،
المحافظة، التاريخ). ضمن حدّ `storefront.*` = ٦٠٠/١٥د، مهاجم يعرف هاتف الضحية يمسح مدى
`ORD-*` فيحصد سجلّ مشترياته.
**الإصلاح:** حدّ معدّل أصرم خاص بـ`trackOrder` (نمط `count.auth` ١٠/دقيقة)، أو إرجاع الحالة
فقط للمسار المجهول بلا تفاصيل بنود/أسعار، أو ربط التتبّع بتوكن HMAC لكل طلب.

### M4 — توليد كلمات المرور المؤقتة بـ`Math.random()` (ليس CSPRNG)
**الملف:** `server/services/userService.ts:154-163` (`generateStrongPassword`)
`Math.random()` (xorshift128+ في V8) قابل للتنبؤ باستعادة الحالة، والبنية ضعيفة ثابتة
(حرف كبير + ٣ صغيرة + ٤-٥ أرقام، بلا خلط، ~٣٠-٣٣ بت). مستعمَل في `userRouter.suggest`
(كلمة مقترحة للمدير) وفي كلمة مدير الشركة الأول عند التوفير (`provisionRequests.ts`).
تخفيف قائم: `mustChangePassword` خلال ٧٢س. **الإصلاح:** `crypto.randomInt(s.length)` + خلط.

### M5 — ترقيم صفحات بلا سقف ⇒ استنزاف ذاكرة (DoS)
**الملفات:** `saleRouter.ts:163-164`, `catalogRouter.ts:177,292`, `purchaseRouter.ts:257`,
`workOrderRouter.ts:119`, `quotationRouter.ts:27`
ستة إندبوينتات تُعرِّف `limit`/`offset` كـ`z.number().default(...)` عارية — بلا `.int()`/
`.max()`/`.min()` — والقيمة تصل `.limit()` بلا قصّ (`paginateKeyset` لا يقصّها). مستخدم
مصادَق يطلب `limit: 100000000` ⇒ محاولة جلب ملايين الصفوف للذاكرة (الأثر يتناسب مع حجم
الجدول)؛ وقيمة سالبة/عشرية ⇒ خطأ MySQL/500. قارن `customerOperationsService.ts:282`
(`Math.min(Math.max(input.limit ?? 50, 1), 500)`).
**الإصلاح:** `z.number().int().positive().max(500).default(50)` على الستة.

### M6 — لا حدّ معدّل على `/api/webhooks/*` (استثناء كامل من الحدّ العام)
**الملف:** `server/index.ts:140` (`skip: ... req.path.startsWith("/api/webhooks")`)
كل طلب webhook مجهول يُشغّل جولة DB + فكّ AES + HMAC قبل أن يفشل التوقيع، بلا أي سقف معدّل.
`GET /whatsapp?hub.verify_token=...` يُشغّل SELECT + SHA-256 لكل صفّ قناة على كل طلب. سطح
استنزاف CPU/DB مجهول الهوية (عامل التضخيم صغير لأن التكاملات = عدد الفروع، لكن غياب أي سقف
هو المشكلة).
**الإصلاح:** حدّ معدّل مستقلّ سخيّ على `/api/webhooks/*` بدل الاستثناء الكامل؛ ورفض الطلب
مبكراً إن كانت ترويسة التوقيع مفقودة/بطول خاطئ قبل استعلام DB.

### M7 — جلسة مدير المنصّة: بلا بصمة جهاز ولا إبطال خادمي + دخول بلا قفل حساب
**الملفات:** `server/tenancy/platformAuth.ts:23-62`, `server/routers/platformAdminRouter.ts:27-43`
توكن مدير المنصّة (يفعّل/يعطّل أي شركة) عمره ٨ ساعات **بلا `fp`** (خلافاً لجلسة المستخدم)
و**بلا `sessionsValidFrom`/sid** ⇒ `logout` يمسح الكوكي فقط ولا يُبطل الـJWT، وتغيير كلمة
المرور لا يُبطل التوكنات القائمة. ودخوله يملك حدّ IP فقط (١٠/١٥د) **بلا قفل حساب** خلافاً
لدخول المستخدم. يصير HIGH فور تفعيل تعدّد الشركات.
**الإصلاح:** أضِف `fp` + عمود `sessionsValidFrom` على `platformAdmins` مع فحصٍ في
`verifyPlatformSession`، وطبّق `registerFailedLogin`/`lockedUntil`.

### M8 — تعطيل شركة لا يُنهي جلساتها الحيّة (kill switch غير فعّال على الجلسات النشطة)
**الملفات:** `server/db.ts:54-64` (`ensureTenantDb`), `server/tenancy/registry.ts:72-83,124-132`
`setCompanyActive(id,false)` يُفرِغ كاش `registry` فقط، لكن `_tenantPools` يحتفظ بالتجمّع
طوال عمر العملية و`ensureTenantDb` لا يعيد فحص `isActive` عند إصابة الكاش. الدخول الجديد
يُحجب، لكن الجلسات القائمة (JWT بـcompanyId) تستمرّ بالوصول الكامل حتى انتهاء الكوكي (حتى
٣٠ يوماً مع «تذكّرني»). **الإصلاح:** أعد فحص `isActive` في `tenancyMiddleware` قبل
`runWithCompany`، وأغلق/أخرج تجمّع الشركة من `_tenantPools` عند التعطيل. (تعدّد الشركات فقط.)

### M9 — «إلزام 2FA للمدير/المشرف» غير مُنفَّذ خادمياً (نصيحة واجهة فقط)
**الملف:** `server/routers/authRouter.ts:130-132`
`login` يُصدر جلسة كاملة لمدير غير مُفعِّل 2FA؛ `mustEnroll2FA` راية واجهة توجيهية فقط —

## ما تحقّقنا من **سلامته** (نتائج سلبية — لا تُعِد فحصها)

**البنية العامة:**
- **لا حقن SQL** في أي مكان: كل `sql`` `` بمعاملات مربوطة، و`sql.raw()` فقط على أسماء أعمدة/
  جداول ثابتة (اختبارات + `stocktake/finalize.ts`). لا بناء SQL من سلاسل، لا ORDER BY/أسماء
  ديناميكية من input (كلها enum-mapped).
- **لا ثغرات تبعيات معروفة** (`pnpm audit --prod` نظيف).
- **لا XSS في الواجهة:** قوالب الطباعة تُهرِّب `[&<>]` عبر `esc()`، والباركود/QR مولّد محلياً
  مع تهريب، وJSX يهرّب افتراضياً. `dangerouslySetInnerHTML` محصور في مكوّنات الباركود/المخطّطات.
- **لا أسرار مُسرَّبة:** لا ملفات أسرار متعقَّبة في git، `.env.*` مستثنى بإحكام، لا أسرار
  مثبّتة في `server/`/`shared/`، والحزمة لا تكشف إلا `VITE_SENTRY_DSN_CLIENT` (عام بطبيعته).

**المتجر العلني:**
- تسعير `createOrder` خادميّ بالكامل من `productPrices` (لا سعر من العميل)، الكمية
  `int().positive().max(999)`، الخصم خادميّ، الفرع مُحلّ خادمياً، والمنتج المخفيّ/الخدميّ/غير
  المنشور مرفوض؛ كله ذرّيّ + idempotent. لا رفع مرفقات عام (`recruitment.submit` بلا `cvFileKey`).

**المصادقة/التشفير:**
- JWT: خوارزمية `HS256` مثبّتة (لا alg=none/confusion)، فصل أغراض التوكن **متبادل ومُنفَّذ**
  (جلسة ترفض أي `purpose`، تذكرة 2FA/كشك/عدّ/منصّة كلٌّ يرفض غرض الآخر)، الدور يُقرأ من DB.
- AES-256-GCM: IV عشوائي ١٢ بايت لكل تشفير، authTag متحقَّق، غياب المفتاح = throw (fail-**closed**).
- scrypt: ملح فريد + `timingSafeEqual` + `DUMMY_STORED` لتوحيد التوقيت. رموز الاسترداد مُهشّمة
  أحادية بمقارنة ثابتة الزمن. الكوكيز `httpOnly + secure + sameSite:strict`.
- إبطال الجلسات (`sessionsValidFrom` + `sid` فردي + إعادة إصدار كوكي المالك بهامش) صحيح.

**webhooks والمسارات الثنائية:**
- HMAC ثابت الزمن، فحص طول قبل `timingSafeEqual`، سرّ غير مضبوط = fail-closed، JSON يُحلَّل
  **بعد** التحقّق. `verify_token` (Meta) مقارنة ثابتة الزمن.
- `/api/backups` قائمة بيضاء صارمة + رفض `..` + فحص dirname + **مدير فقط**. `/api/img` و
  `/api/wa/media` مفاتيح أعداد صحيحة (لا traversal) + قائمة MIME بيضاء + nosniff + attachment.

**التفويض (RBAC):**
- البندان اللذان أشار إليهما التدقيق المالي مُصلَحان فعلاً: `globalSearch/rbac.ts` يستعمل
  `hasModuleAccess`، و`shift.report` يقرأ `report.shift.branchId` الصحيح.
- الخدمة الذاتية سليمة (`commissions.myStatus`/`courier.*`/`countPortal.mine` تحلّ الهوية من
  `ctx.user` حصراً). تصعيد الصلاحيات مغلق (`userRouter`/`roleRouter` على `adminProcedure`).

**تعدّد الشركات (مسار الطلب الحيّ):**
- `companyId` حصراً من JWT موقّع، والهوية تُتحقَّق **داخل** قاعدة الشركة المستهدفة (لا حقن

  تعدّد الشركات. TOCTOU لتفرّد الرمز مُغلق بقيد DB. حقن الأوامر في التوفير مُغلق (`execFile` +
  `CODE_RE`). تسريب `CONTROL_DATABASE_URL` للعمليات الفرعية مُصلَح.
