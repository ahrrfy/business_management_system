# تحسين أداء توليد محتوى المنتجات بالجملة وتصميم واجهة المراجعة

## 1. القرار المعماري المختصر

لا ينبغي أن ينتظر الموظف استجابة الذكاء الاصطناعي أثناء حفظ المنتج، ولا ينبغي استدعاء النموذج مع كل حرف يكتبه. أفضل تصميم هو:

```text
حفظ المنتج والحقائق الأساسية
        ↓
حساب بصمة الحقائق والسياسة
        ↓
قراءة Cache أو إنشاء مهمة خلفية
        ↓
توليد مسودة AI على دفعات صغيرة
        ↓
Zod + تحقق دلالي
        ↓
حفظ المسودة فقط
        ↓
مراجعة الموظف
        ↓
اعتماد ونشر المحتوى
```

الذكاء الاصطناعي لا يغيّر `products.name` أو `products.description` مباشرة. إنه ينتج مسودة مرتبطة بنسخة محددة من حقائق المنتج وسياسة الـPrompt.

## 2. ممارسات الأداء عند الإضافة بالجملة

### عدم التوليد أثناء الكتابة

يجب أن يكون التوليد عند ضغط الموظف على «اقتراح محتوى» أو عند بدء مهمة جماعية. لا تستخدم `onChange` لكل حقل لاستدعاء LLM. يمكن استخدام debounce للبحث المحلي أو فحص التكرار، لكن توليد النص نفسه يجب أن يكون فعلاً مقصوداً من المستخدم.

### التمييز بين التوليد الفوري والتوليد الجماعي

| الحالة | السلوك الأفضل | سبب الاختيار |
|---|---|---|
| منتج واحد أثناء الإنشاء | استدعاء فوري مع زر إلغاء | الموظف يريد نتيجة سريعة قبل الحفظ |
| 2–20 منتجاً | دفعة صغيرة أو عدة مهام محدودة التوازي | تقليل عدد الاتصالات مع الحفاظ على دقة الإخراج |
| مئات أو آلاف المنتجات | Queue خلفية مع تقدم واستئناف | عدم حجز طلب HTTP وعدم فقدان التقدم عند الخطأ |
| منتج لم تتغير حقائقه | قراءة Cache | منع استدعاء مكرر |
| تغيرت الحقائق أو السياسة | Cache miss مقصود | ضمان عدم استخدام مسودة قديمة |

حجم الدفعة ليس رقماً ثابتاً؛ يضبط حسب طول الوصف وعدد الحقول وحد النموذج. عملياً، ينبغي البدء بدفعات صغيرة، ثم اختبار الحجم الذي يبقى معه JSON صحيحاً وزمن الاستجابة مستقراً. إذا فشل عنصر واحد داخل دفعة، لا تجعل النظام يعيد الدفعة كلها؛ أعد العنصر الفاشل منفرداً أو ضمن دفعة أصغر.

### تحديد التوازي

استخدم عدداً محدوداً من العمال، مثل 2 إلى 4 في البداية، مع حد أقصى قابل للضبط. التوازي غير المحدود يؤدي إلى ازدحام، أخطاء مؤقتة، ومخرجات متقطعة. كل عامل يأخذ عنصراً أو دفعة من Queue، ويضع قفلاً يمنع تشغيل مهمتين نشطتين لنفس المنتج والبصمة.

### إعادة المحاولة الصحيحة

أعد المحاولة فقط للأخطاء المؤقتة مثل انقطاع الاتصال أو المهلة أو الاستجابة غير المتاحة. استخدم exponential backoff مع jitter، مثلاً 1 ثم 2 ثم 4 ثم 8 ثوانٍ ضمن سقف محدد. لا تعِد المحاولة على خطأ Zod أو خطأ حقائق؛ هذه أخطاء محتوى تحتاج إصلاحاً أو مراجعة، وليست مشكلة اتصال.

### عدم استخدام Streaming للدفعات

في المنتج الفردي قد يكون البث مفيداً للإحساس بسرعة الواجهة، لكن في الدفعات لا تحتاج إلى عرض JSON جزئي للموظف. الأفضل انتظار كائن كامل قابل للتحقق، ثم عرض النتيجة بعد `safeParse`. هذا يبسط التعامل مع الفشل ويمنع عرض مسودة ناقصة.

## 3. تصميم Cache صحيح

### مفتاح Cache يعتمد على نسخة الحقائق

لا تجعل المفتاح مبنياً على `productId` وحده؛ لأن المنتج قد يتغير. استخدم بصمة تشمل:

```text
productId
canonical verified facts
variant facts
channel
locale
promptVersion
categoryPolicyVersion
modelId
```

مثال:

```ts
import { createHash } from "node:crypto";

function contentFingerprint(input: unknown): string {
  const canonical = stableStringify(input); // ترتيب ثابت للمفاتيح والمصفوفات
  return createHash("sha256").update(canonical).digest("hex");
}

function makeCacheKey(input: {
  facts: ProductFacts;
  channel: string;
  locale: string;
  promptVersion: string;
  policyVersion: string;
  modelId: string;
}) {
  const fingerprint = contentFingerprint(input);
  return `ai-product-content:v3:${fingerprint}`;
}
```

`stableStringify` يجب أن يرتب مفاتيح الكائنات قبل تحويلها إلى JSON؛ وإلا قد ينتج نفس المحتوى مفاتيح مختلفة بسبب ترتيب الحقول.

### ما الذي يُخزَّن؟

الأفضل تخزين النتيجة والتحقق معاً، لا النص فقط:

```text
aiContentCache
- id
- cacheKey UNIQUE
- productId
- factsFingerprint
- promptVersion
- policyVersion
- modelId
- locale
- channel
- responseJson
- validationJson
- status: VALID | INVALID | EXPIRED
- createdAt
- expiresAt
```

تخزين Cache في جدول قاعدة البيانات مناسب كبداية لأنه قابل للتدقيق والاستعادة. يمكن إضافة Redis كطبقة سريعة لاحقاً، لكن لا تجعله المصدر الوحيد للمسودات أو لقرارات الاعتماد.

### متى تُلغى Cache؟

لا تعتمد على وقت الانتهاء فقط. يجب اعتبار النتيجة قديمة فوراً إذا تغير أحد الآتي:

| التغيير | الإجراء |
|---|---|
| تغير الماركة أو النوع أو الموديل | إعادة التوليد |
| تغير السمات مثل المقاس أو السعة أو المادة | إعادة التوليد |
| تغير المتغير أو الوحدة | إعادة توليد POS والفاتورة، وقد لا تحتاج إعادة الوصف العام |
| تغير سياسة الفئة | إعادة التحقق أو التوليد |
| تغير Prompt | Cache miss عبر `promptVersion` جديد |
| تغير النموذج | Cache miss اختياري أو مراجعة الجودة |
| تعديل الموظف للمسودة | حفظ نسخة يدوية منفصلة وعدم الكتابة عليها بالـCache |

### Cache للطلبات المتطابقة أثناء التنفيذ

عند وصول طلبين متزامنين لنفس البصمة، لا ترسل طلبين للنموذج. أنشئ سجل مهمة بحالة `RUNNING` أو استخدم قفل قاعدة بيانات/مفتاح idempotency. الطلب الثاني يراقب المهمة القائمة أو يعيد النتيجة عند اكتمالها.

## 4. تصميم مهمة الدفعة

يُنصح بوجود جدولين:

```text
aiContentJobs
- id
- requestedBy
- status: QUEUED | RUNNING | PAUSED | COMPLETED | FAILED | CANCELLED
- totalItems
- completedItems
- failedItems
- promptVersion
- policyVersion
- createdAt
- startedAt
- finishedAt
- errorSummary
```

```text
aiContentJobItems
- id
- jobId
- productId
- factsFingerprint
- status: QUEUED | CACHE_HIT | RUNNING | DRAFT_READY | VALIDATION_FAILED | FAILED
- draftId
- attempts
- lastError
- startedAt
- finishedAt
```

تتم معالجة كل عنصر بشكل idempotent. إذا انقطع العامل، يستطيع النظام استئناف العناصر التي بقيت `QUEUED` أو `RUNNING` منذ مدة تتجاوز مهلة العامل. لا تعيد العناصر `DRAFT_READY` إلا إذا تغيرت بصمتها.

## 5. واجهة المستخدم المقترحة

### شاشة المنتج الفردي

أقترح أن يكون قسم المحتوى عبارة عن لوحة مراجعة لا Textarea واحداً. في اليمين تظهر **الحقائق الأساسية المقفلة للقراءة**، وفي الوسط المسودة القابلة للتحرير، وفي اليسار معاينة القنوات.

```text
┌────────────────────┬──────────────────────────┬────────────────────┐
│ حقائق المنتج       │ مسودة AI قابلة للتعديل   │ معاينة القنوات     │
│ النوع              │ عنوان SEO                │ المتجر             │
│ الماركة            │ اسم مختصر                │ POS                │
│ المقاس             │ اسم الفاتورة             │ الفاتورة            │
│ السعة              │ نص ترويجي                │ الملصق              │
│ المتغيرات           │ وصف فني                  │                    │
│ الأدلة المعتمدة    │ [تطبيق] [تعديل]          │                    │
└────────────────────┴──────────────────────────┴────────────────────┘
```

في الهاتف تتحول الأعمدة إلى تبويبات: **الحقائق، المسودة، المعاينة**. يجب أن تبقى واجهة RTL، مع إبقاء الحقول الرقمية وSKU والباركود في اتجاه LTR عند الحاجة.

### مكونات الواجهة

| المكوّن | الوظيفة |
|---|---|
| `GenerateContentButton` | يبدأ التوليد ويعرض الحالة والزمن وإمكانية الإلغاء |
| `FactsSummaryPanel` | يعرض الحقائق التي استند إليها AI، ولا يسمح بتعديلها من داخل المسودة |
| `DraftFieldCard` | حقل مستقل مع النص الحالي والجديد وزر تطبيق وتراجع |
| `EvidenceBadges` | يوضح الأدلة التي استخدمها كل ادعاء |
| `ValidationBanner` | يعرض أخطاء Zod والأخطاء الدلالية بصيغة قابلة للإصلاح |
| `ChannelPreviewTabs` | معاينة المتجر وPOS والفاتورة قبل الاعتماد |
| `BulkJobProgress` | عدد المنجز والفاشل والمتبقي مع إعادة المحاولة الانتقائية |
| `ApprovalBar` | اعتماد الحقول أو حفظ المسودة أو رفضها |

### حالة الحقل الواحد

كل حقل ينبغي أن يمر بهذه الحالات:

```text
EMPTY → GENERATING → DRAFT_READY → EDITED → VALIDATED → APPROVED
                         ↓
                 VALIDATION_FAILED
```

إذا عدّل الموظف حقلاً يدوياً، يظهر شريط صغير «تم تعديل هذا الحقل يدوياً» مع زر «إرجاع اقتراح AI». عند توليد نسخة جديدة لا تُمحى النسخة اليدوية؛ تحفظ كنسخة سابقة وتظهر مقارنة قبل/بعد.

### المقارنة قبل الاعتماد

لا تعرض المسودة وحدها. اعرض:

| جانب المقارنة | ما يظهر |
|---|---|
| القيمة الحالية | الاسم أو الوصف المنشور حالياً |
| اقتراح AI | النص الجديد |
| سبب الاقتراح | ترتيب الحقول أو تقليل الطول أو إزالة التكرار |
| الأدلة | الحقول التي استند إليها النص |
| التحذيرات | ما يحتاج قراراً بشرياً |
| المعاينة | كيف سيظهر في المتجر أو الفاتورة |

يفضل استخدام إبراز التغييرات داخل النص، مع عدم الاعتماد على اللون وحده؛ استخدم أيضاً عبارة واضحة مثل «أضيفت عبارة» أو «حُذفت كلمة».

## 6. تجربة الدفعة بالجملة

يبدأ الموظف بتحديد المنتجات أو رفع ملف، ثم تظهر شاشة إعداد بسيطة: اللغة، القنوات المطلوبة، هل نولّد الوصف أم العنوان فقط، وهل نستخدم Cache عند تطابق الحقائق. بعد بدء المهمة تظهر قائمة قابلة للفرز:

| المنتج | الحالة | الجودة | الإجراء |
|---|---|---|---|
| دفتر سلك A5 | مسودة جاهزة | عالية | مراجعة |
| قلم حبر 0.7 | فشل التحقق | يحتاج قياساً | إصلاح |
| كتاب الرياضيات | من Cache | مطابقة الحقائق | مراجعة |
| طباعة A4 | قيد التوليد | — | إلغاء |

لا تطلب من الموظف مراجعة كل المنتجات بالطريقة نفسها. أعطه مرشحاً سريعاً: «أظهر فقط الفاشل»، «أظهر فقط الذي يحتوي تحذيرات»، «أظهر المنتجات الأكثر مبيعاً»، أو «اعتماد المسودات التي لا تحتوي تحذيرات». ويجب أن يبقى الاعتماد الجماعي مشروطاً بمرور التحقق وعدم وجود تحذيرات حرجة.

## 7. الأداء في React وtRPC

في الواجهة لا تستخدم mutation لكل صف أثناء الرسم. استخدم mutation لإنشاء `jobId` فقط، ثم:

```ts
const startJob = trpc.catalog.startContentJob.useMutation();
const job = trpc.catalog.contentJob.useQuery(
  { jobId },
  { enabled: jobId != null, refetchInterval: (query) => {
      const status = query.state.data?.status;
      return status === "QUEUED" || status === "RUNNING" ? 1500 : false;
    }}
);
```

إذا كان النظام يحتاج تحديثاً فورياً، يمكن استخدام SSE أو WebSocket لاحقاً، لكن polling الخفيف لحالة المهمة أبسط كبداية. يجب إيقافه تلقائياً عند `COMPLETED`, `FAILED`, أو `CANCELLED`.

في شاشة المنتج الفردي استخدم cache محلياً لمسودة الحقل، واحتفظ بـ`factsFingerprint` مع المسودة. إذا تغيرت الحقائق قبل الاعتماد، أظهر رسالة: «هذه المسودة مبنية على نسخة قديمة من البيانات؛ حدّث الاقتراح قبل الاعتماد».

## 8. ما الذي يجب ألا يحدث؟

لا تستدعِ النموذج داخل عملية `createProduct` الحرجة بحيث يفشل حفظ المنتج كله بسبب مهلة AI. لا تضع API key في المتصفح. لا تسمح للمستخدم بتمرير `verifiedClaims` غير مصرح بها من الواجهة. لا تستخدم Cache بمفتاح `productId` فقط. لا تعيد المحاولة بلا حد. لا تعتمد المسودة تلقائياً لمجرد أن JSON صحيح. ولا تُخفِ فشل التحقق خلف كلمة عامة مثل «تعذر التوليد»؛ يجب إظهار هل الفشل اتصال، JSON، أو تعارض حقائق.

## 9. مقارنة خيارات التنفيذ

| الخيار | المزايا | المقايضات | التعقيد |
|---|---|---|---|
| توليد فوري عند الطلب | سريع التنفيذ ومناسب لعدد قليل | لا يناسب آلاف المنتجات ولا الانقطاع | منخفض |
| Queue داخل الخادم مع جدول مهام | استئناف، تقدم، Retry، Cache، مراجعة جماعية | يحتاج عامل خلفي ومراقبة | متوسط |
| Queue خارجية مثل Redis/BullMQ | تحكم قوي وتوازي أفضل | بنية إضافية وصيانة أكبر | مرتفع |

البدء الأنسب للنظام الحالي هو **جدول مهام في قاعدة البيانات مع عامل محدود التوازي**، ثم إضافة Redis فقط إذا أثبتت الأحجام الفعلية أن قاعدة البيانات أصبحت عنق زجاجة.

## الخلاصة

الأداء لا يأتي من جعل النموذج أسرع فقط، بل من تقليل الاستدعاءات غير الضرورية، وإعادة استخدام النتائج المتطابقة، وتشغيل الدفعات خارج طلب الموظف، وتجزئة الفشل، وربط كل مسودة ببصمة الحقائق ونسخة السياسة. أما واجهة الاستخدام الناجحة فتفصل بين **الحقائق** و**المسودة** و**المعاينة**، وتسمح بتطبيق كل حقل منفرداً، وتكشف الأدلة والتحذيرات، وتحافظ على تعديلات الموظف ولا تعتمد شيئاً تلقائياً.
