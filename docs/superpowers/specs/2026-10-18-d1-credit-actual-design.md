# Actual credit sale and collection on D1 — isolated design

User authorization: implement actual stocked credit POS sale and subsequent collection, all financial effects, recovery and replay, without production changes or a paid upgrade. This extends the approved original-service lab architecture; no new business policy or production routing is introduced.

- Reuse the original `createConfirmedPosSaleInTx`, `processPayment`, credit limit, contract pricing, inventory, ledger and FIFO auto-settlement services. Capture their SQL in private SQLite, then commit the exact validated changes in one native D1 batch. Use Decimal for the exact original customer-balance increment; never SQLite floating-point money arithmetic.
- Keep cash117/cloud and all prior proof data intact. Credit uses original-name tables added beside existing `lab_*` tables in two old feasibility databases; its independent signed journal uses new `cashJournal*` tables beside `edge_*` in the old edge journal database. Preflight must prove names disjoint, exact account/UUID/creation identity, and record prior tables/rows before any additive initialization. Preserve and compare legacy data afterward. No new D1 or plan upgrade is needed if these verified boundaries hold.
- Share the tested plan applier, scoped snapshot engine, immutable journal, keyset export and FIFO queue. Add explicit configuration and static build boundaries; cash defaults must remain byte/behavior compatible. Credit has a distinct lab identity and schema version. Sale and collection share one global credit writer and epoch.
- Read the requested customer, units/contracts, and COMPLETE customer open-invoice FIFO closure across branches, target invoice/payment replay closure, posting gates, actor/shift and relevant stock/holds. Reject any related delivery history before entering original services; approval bypasses, COD, opening waivers, digital/service/bundle sales and non-CASH collections remain unsupported and fail closed. Do not substitute empty financial dependencies.
- Bind original `processPayment` transaction callback to the private staging transaction through AsyncLocalStorage. Keep the original financial gate. Capture post-commit hooks without executing them during staging; durable financial-change outbox is committed with the financial effects. No notifications/publication/network side effects are performed in this lab.
- Command replay returns the saved original result BEFORE rerunning services, including after collection changes invoice status/payment method. Every successful acknowledgement requires both primary and signed independent journal. Restore applies verified records to the independent target without binding the source.
- Traditional Arabic lab UI: existing synthetic customer/product, credit/initial CASH payment, subsequent partial/final CASH collection, stable saved request IDs with status lookup, and current invoice/customer/receipt/stock/ledger evidence. Private token is laboratory authentication only.
- Verify zero-payment and initial-partial credit, partial/final/overpayment, customer limits and concurrency, Decimal cents/large balances, contracts/FIFO/prior credit, identity/shift/date/period rejection, exact replay after later changes, faults around PREPARED/primary/ACK, real writer restart, interrupted/resumed export and source-disposed restore. Compare against actual original MySQL effects, run full original ERP suite once on owned fresh isolated MySQL, and finish with a small cloud lifecycle only.

Cost controls: native local financial/load/recovery trials; reuse the existing eight cloud databases and current account plan; cloud proof only after native safety passes.
