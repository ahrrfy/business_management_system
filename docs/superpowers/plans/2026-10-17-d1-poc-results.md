# نتائج مختبر D1 المعزول للكاشير والمتجر

التاريخ: 2026-10-17، بغداد. مرجع النظام: `5d8a072699c301a64bf9fe8620bea9c919244c4b`.

القرار: نجح إثبات الجدوى المحلي للأوامر التمثيلية واجتاز المراجعة المستقلة؛ يُسمح بمتابعة المحوّل المعزول. اعتماد الإنتاج يبقى No-Go إلى حين إغلاق البوابات أدناه.

## نطاق الإثبات

مختبر مستقل في `experiments/d1-continuity`، ببيانات اصطناعية، على Node 24 وMiniflare/workerd مع D1 محلية، ومقارنة MySQL 8.4.9 منفصلة على loopback:13317. لا استيراد `.env` ولا حسابات الإنتاج ولا مزوّد بطاقات/دفع حقيقي. لم تُعدّل خدمات النظام أو مخططه أو DNS أو اشتراكات Cloudflare أو Hostinger.

النموذج يمثل حدود أوامر مالية مشتركة: بيع نقدي/آجل، حجز طلب المتجر وإرساله COD، مرتجع، موافقة/كوبون، ونية إصدار رقمية اصطناعية. لا يشغّل خدمات ERP الأصلية كاملة، ولا يستضيف واجهتي الكاشير والمتجر؛ إثبات جميع الوظائف يتبع هذا المختبر ولا يُستنتج منه.

## المال وقاعدة المقارنة

- شُغّلت دوال `server/services/money.ts` و`billing.ts` الأصلية دون تعديل، بعد تجميعها في الذاكرة. سجل الأدلة يحفظ SHA256 للمصدرين.
- مقارنة حدود HALF_UP والمبالغ الموجبة والسالبة والكسور ومجال DECIMAL(20,2)، ومنها `999999999999999999.99`؛ المقارنة تشمل حفظ MySQL وإرجاع D1 كسلاسل نصية.
- التخزين النصي مع حساب Decimal دقيق يسمح بالحفاظ على المجال؛ **لا يسمح باستعمال SUM/CAST العددي المعتاد للنصوص ثم ادعاء الدقة**. تجميع القيمة القصوى عددياً يفقد كسورها عند العودة عبر API؛ المقارنات والفرز المالي للنصوص يحتاجان عقداً صحيحاً أيضاً.
- اختبار المقارنة كشف اختلافاً في النموذج: خصم الفاتورة الأكبر من الإجمالي يجب قصّه إلى الإجمالي مثل الخدمة الأصلية. أُصلح النموذج وأُعيد الاختبار بنجاح؛ لم تتغير سياسة الإنتاج.
- اختبار تداخل زمني كشف احتمال إعادة خطأ نفاد مخزون لمحاولة مكررة اكتمل أصلها بعد فحص التكرار الأول. أُضيف استرداد النتيجة المحفوظة بالهوية والحمولة الأصليتين قبل إعادة خطأ القبول، ونجح اختبار التداخل المتعمد. كذلك لا ينشئ النموذج إيصال نقد بقيمة صفر عند تقريب مرتجع جزئي إلى صفر.
- اختبار `utf8mb4_unicode_ci` الفعلي في MySQL المختبر كشف اختلاف accent/PAD مع SQLite BINARY/NOCASE؛ يجب تثبيت عقد تطبيع المعرفات وفحص التصادمات. لم تُقرأ collation الإنتاج.
- لا تشمل النتيجة كل حسابات الكلفة وWAVG والعملات وأسعار شراء USD بأربع مراتب أو تقارير SQL الحالية. هذه عقود ترحيل مستقلة إلزامية.

## سجل التحقق

الأدلة التفصيلية في `experiments/d1-continuity/results`، وأوامر الإعادة في README للمختبر. تشغيل D1 أنهى عمليته بنجاح؛ لا يعتمد التقرير على مخرجات اختبارات بقيت معلقة.

- `pnpm check`: ناجح على رأس الأساس وخدمات الإنتاج غير المعدلة.
- `pnpm check:guards`: ناجح.
- اختبارات المال الحالية `moneyPrecision` و`moneySchemas`: 13/13 ناجحة، TZ=UTC.
- اختبارات D1 السلوكية: 28/28 ناجحة، مع فحص الحالة المالية والمخزنية الناتجة والتنافس وإعادة التشغيل المحلي.
- المقارنة مع المصدر وMySQL: 6/6 ناجحة، تتضمن 263 متجه تقريب/حدود و5 سيناريوهات إجمالي فواتير. تطابق المجموع الدقيق `0.03` بين MySQL وDecimal، بينما SUM العددي للقيمة القصوى أعاد `1000000000000000000` وفقد الكسور.
- اختبار هوية MySQL والعزل: 2/2 ناجحة؛ محاولة تجهيز بمرجع data directory خاطئ رُفضت ولم يتغير عداد CREATE DATABASE.
- المراجعة المستقلة: اجتاز مطابقة المتطلبات وجودة الكود بعد إغلاق الملاحظتين؛ لا ملاحظة مادية متبقية ضمن نطاق النموذج.

كشفت المراجعة نقطتين وأُصلحتا ثم أُعيدت الفحوص: قيد تنسيق يقبل `1..0` و`1.0.`، ونافذة سباق في تجهيز MySQL قبل التحقق من هويتها. القيود الآن ترفض المتجهين في الأعمدة المالية الأربعة عشر للمختبر؛ التجهيز يتحقق من العملية والمستمع وdatadir/port ثم ينشئ القاعدة على الاتصال الموثق نفسه. أُقرت الإصلاحات في إعادة المراجعة.

الحزمة الكاملة لتكامل ERP لم تُشغّل في هذه التجربة: لا تغيير في منطق الإنتاج أو مخططه؛ فحوص هذه التجربة مستقلة، ولا تعتبر بديلاً عن الحزمة الكاملة المطلوبة عند تنفيذ المحوّل المالي الحقيقي.

## حدود توقف Hostinger وفقد البيانات

1. فشل Hostinger ممثل بربط خدمة غير متاح وحظر اتصالات Worker الخارجية؛ المطلوب أن تنجح أوامر المختبر دون الرجوع إليه. هذا ليس تمرين فصل لخادم الإنتاج.
2. سيناريو فقد الرد بعد الالتزام يجب أن يعيد نفس المستند والنتيجة مع نفس الحمولة والمفتاح، مع أثر مالي ومخزني واحد. فشل آخر تعليمة يجب أن يرجع كل الصفوف السابقة.
3. إعادة تشغيل runtime مع نفس التخزين تثبت بقاء البيانات بعد إعادة تشغيل العملية المحلية. لا تثبت النجاة من تلف القرص أو فقد موقع Cloudflare أو صحة Time Travel/الاستعادة.
4. رفض epoch قديم يثبت حراسة حد أمر المختبر؛ **لا يثبت سحب صلاحيات SQL من كتّاب Hostinger الحقيقيين**. عزل أولئك الكتاب ومهامهم وإغلاق المعاملات العابرة يبقى شرط القطع.
5. منع تكرار الأثر الداخلي لا يثبت أن مزود بطاقة/دفع خارجي نفذ مرة واحدة. نتيجة UNKNOWN تتطلب مصالحة، ولا تسمح بإعادة الإصدار تلقائياً.

## البوابات المتبقية

- اختبار D1 سحابية منفصلة: لم يبدأ؛ `wrangler whoami` أظهر عدم تسجيل الدخول. لا قاعدة سحابية أو Worker منشأ ولا اشتراك مفعّل في هذه التجربة.
- حجم النواة والفهارس والنمو وحد 10GB، حمل الكاشيرات والمتجر وP95/CPU/rows والكلفة الفعلية: لم تقاس سحابياً.
- تحويل مخطط الشركة وقيوده ومقارنة النصوص وتقارير المال، وكل كتّاب المخزون والنقد والائتمان والإقفال: لم ينفذ.
- هوية ERP الكاملة والصلاحيات والأجهزة، الصور والخطوط والطباعة الفعلية، وكل وظائف الرقمي والمتجر والتوصيل: لم تُرحّل.
- نسخة مستقلة مع استعادة ومصالحة كل عملية مؤكدة بعد نقطة الاستعادة، وبيانات الاختبار السحابية: لم تثبت.

لا انتقال للإنتاج أو وعد بعدم فقد أي بيانات قبل إغلاق هذه البوابات. نجاح المختبر يبرر متابعة النموذج المعزول؛ تشغيل النظام الحقيقي يحتاج أدلة بوابات الترحيل والتعافي كاملة.
