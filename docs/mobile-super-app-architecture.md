# معمارية تطبيق الجوال المركزي (Super App)

## الهدف

تطبيق واحد لكل موظف، يتغير محتواه حسب هويته ودوره وفرعه وصلاحياته الفعلية. لا تكون الموارد البشرية تطبيقاً منفصلاً ولا تكون العمليات نسخة مصغرة من سطح المكتب: يرى المستخدم «يومي» أولاً، ثم الأدوات والبيانات المصرّح بها فقط.

## ما هو موجود ويُعاد استعماله

- `shared/permissions.ts`: القوالب الأساسية للأدوار ومستويات `FULL / READ / NONE`.
- `server/trpc.ts` و`server/context.ts`: فرض الصلاحيات ونطاق الفرع والأدوار المخصصة.
- `attendanceRouter` وخدمة الحضور: مصدر جهاز البصمة محمي؛ لا يسمح للهاتف بأن يزعم أن مصدره `fingerprint`.
- `payrollRouter` و`tasksRouter`: مصادر الراتب والمهام الحالية.
- `pushRouter` و`pushService`: أساس Web Push واشتراكات الأجهزة.

## طبقات التطبيق

```text
تطبيق Android / iOS
  App Shell (جلسة، فرع، لغة، اتصال، تحديث)
  ├─ الصفحة الرئيسية المخصصة للدور
  ├─ مساحة العمل (الوحدات المسموح بها)
  ├─ مركز التنبيهات
  └─ ملفي (حضور، راتب، إجازات، مهام)
            │ tRPC / HTTPS + Web Push
بوابة الهوية والصلاحيات
  ├─ الدور الأساسي + الدور المخصص + استثناءات المستخدم
  └─ نطاق الفروع
            │
خدمات المجال: مبيعات | مخزون | مهام | حضور | رواتب | موافقات
            │ أحداث نطاق العمل (Domain Events)
سجل أحداث موثوق (Outbox) → مركز الإشعارات → داخل التطبيق / Push / بريد عند الحاجة
```

## بوابة المستخدم الشخصية

تبقى ظاهرة لكل مستخدم حتى لو كانت صلاحياته التشغيلية محدودة:

- سجل حضور اليوم، دخول/خروج، وسجل الأيام السابقة.
- بطاقة الراتب: الراتب المتوقع، السلف، العمولات، وحالة مسير الرواتب. لا تظهر تفاصيل رواتب الآخرين إلا بصلاحية HR.
- المهام الموكلة والمهام التي أنشأها المستخدم، مع موعد الاستحقاق وحالة التنفيذ.
- الإجازات، الطلبات الشخصية، ملف العمل، وإعدادات الإشعارات.

الحضور من الهاتف يكون طلب حضور موثقاً بموقع/جهاز أو طلب تصحيح عند الحاجة. أما حدث جهاز البصمة فيأتي من تكامل الجهاز الخادمي فقط، ويحمل `source=fingerprint` من الخادم، لا من العميل.

## تصميم الإشعارات

### نموذج البيانات المقترح

إضافة كيانات مستقلة إلى جانب `pushSubscriptions` الحالية:

- `notifications`: المالك `userId`، الشركة/الفرع، النوع، الأولوية، العنوان، النص المختصر، الرابط/المورد، وقت الإنشاء والانتهاء والقراءة.
- `notificationDeliveries`: لكل قناة (`in_app`, `push`, `email`) مع الحالة ووقت الإرسال والفشل.
- `notificationPreferences`: تفضيلات المستخدم حسب نوع التنبيه وقناة التوصيل وساعات الهدوء.
- `eventOutbox`: حدث عمل مسجل في المعاملة نفسها قبل محاولة الإرسال؛ يعاد تشغيله بأمان عند تعطل الخدمة.

### الأولويات والسلوك

| الأولوية    | داخل التطبيق                               | Push                 | مثال                                |
| ----------- | ------------------------------------------ | -------------------- | ----------------------------------- |
| حرجة        | نافذة واضحة قابلة للإغلاق + مركز التنبيهات | فوري                 | فرق صندوق، صلاحية أمنية، توقف عملية |
| إجراء مطلوب | بطاقة ثابتة في المركز وزر واحد أو اثنان    | فوري أثناء الدوام    | اعتماد طلب شراء، مهمة تجاوزت الموعد |
| عادية       | شارة وقائمة نشاط                           | مجمّع أو حسب التفضيل | إنشاء مهمة، استلام طلب              |
| معلوماتية   | سجل فقط                                    | لا                   | نجاح مزامنة أو تحديث حالة           |

التنبيه المنبثق لا يُستخدم للتسويق أو لتكرار نفس الحدث. كل تنبيه يجب أن يفتح صفحة المورد الصحيح أو ينفذ إجراءً محدوداً. قبل تنفيذ أي إجراء من التنبيه يعاد فحص الصلاحية في الخادم؛ لا يكفي أن يكون الزر ظاهراً في الهاتف.

## تدفق حدث نموذجي

1. يعتمد مدير المخزن استلام توريد.
2. معاملة الاستلام تسجل سجل المراجعة وحدث `inventory.receipt.created` في `eventOutbox`.
3. عامل الإشعارات يحدد المستلمين من الدور، الفرع، مالك المهمة، والتفضيلات.
4. ينشئ سجل الإشعار داخل التطبيق أولاً، ثم يحاول Push للأجهزة المسجلة.
5. فتح الإشعار يمرر `notificationId` و`resourceType/resourceId`؛ يسجل القراءة ثم يفتح المورد بعد التحقق من الصلاحيات.

هذا يمنع ضياع التنبيه عندما يتوقف Push أو يكون الهاتف غير متصل، ويمنع إرسال معلومة فرع إلى مستخدم خارج نطاقه.

## واجهة الجوال

- **الرئيسية:** ملخص وردية، إجراءات سريعة، عناصر تحتاج تدخلاً، وبطاقات مختلفة حسب الدور.
- **العمل:** فقط الوحدات التي تسمح بها خريطة الصلاحيات؛ لا نعتمد على إخفاء الروابط كوسيلة أمنية.
- **مركز التنبيهات:** قائمة موحدة مع فلترة (مطلوب إجراء / مهام / موارد بشرية / معلومات) وإجراءات مباشرة.
- **ملفي:** بوابة الموظف الشخصية المذكورة أعلاه.
- **زر الإجراء المركزي:** قائمة إجراءات مسموحة للدور الحالي؛ لا يعرض مثلاً «بيع سريع» لمستخدم المخزن.

## حدود الأمان والخصوصية

- القرار النهائي للصلاحية ونطاق الفرع في الخادم فقط.
- لا تظهر الرواتب، التكلفة، أو بيانات موظف آخر في Push. Push يحمل عنواناً موجزاً ورابطاً آمناً فقط.
- لا تنفذ عمليات مالية حساسة من Push دون تأكيد داخل التطبيق، وسجل مراجعة، وإعادة تحقق من الجلسة.
- تربط اشتراكات الأجهزة بالمستخدم وتلغى عند تسجيل الخروج أو تعطيل الحساب.

## مراحل التنفيذ

1. توحيد `Mobile Bootstrap`: هوية المستخدم، الفرع، خريطة الصلاحيات، العداد غير المقروء، وملخص اليوم.
2. إطلاق «ملفي» للموظف: الحضور والمهام والراتب ضمن صلاحياته.
3. بناء مركز إشعارات داخل التطبيق و`eventOutbox`، ثم توسيع Push ليشمل جميع الأدوار بحسب نوع الحدث.
4. نقل الوحدات التشغيلية ذات الأولوية إلى مساحات جوال مستقلة: البيع، المخزون، الموافقات.
5. إضافة مزامنة دون اتصال للعمليات الآمنة فقط مع طابور عمليات ومعالجة تعارضات على الخادم.
