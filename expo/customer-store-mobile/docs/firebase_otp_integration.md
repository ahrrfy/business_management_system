# Firebase OTP والنظام الأساسي

## قرار التنفيذ

يعتمد تطبيق «مكتبة العربية» **Firebase Phone Authentication** لإثبات ملكية رقم الهاتف قبل عرض أو صرف نقاط الولاء والقسائم الشخصية. بعد نجاح التحقق، يرسل التطبيق رمز Firebase ID إلى النظام الأساسي؛ ويتحقق الخادم من الرمز، ويطابق الهاتف بصيغته المعيارية `+964…` مع سجل العميل، ثم يجعل رصيد الولاء والقسائم والتسعير النهائي متاحة للجلسة الموثقة فقط.

## حالة إعداد المشروع

أُنشئ مشروع Firebase مستقل للعملاء باسم **Store alarabiya** ومعرّف مشروع `store-alarabiya`، منفصل عن مشروع التطبيق الإداري. هذا الفصل يمنع اختلاط أجهزة الموظفين بحملات العملاء أو إعدادات تسجيل الهاتف.

## متطلبات Firebase الرسمية

وفق [دليل Expo لاستخدام Firebase](https://docs.expo.dev/guides/using-firebase/) (آخر تحديث ظاهر: 17 يوليو 2026)، يدعم Firebase JS SDK استخدام Expo Go للتطوير، ويتطلب إصدار `firebase@12.0.0` أو أحدث. أما React Native Firebase فيعتمد كوداً أصلياً مخصصاً ولا يعمل في Expo Go؛ لذلك يكون مناسباً لاحقاً لبناء إنتاجي مخصص، لا لجلسات QR الحالية.

وفق [دليل Firebase Phone Authentication](https://firebase.google.com/docs/auth/web/phone-auth) (آخر تحديث ظاهر: 13 أغسطس 2026)، يلزم تمكين Phone provider، وضبط سياسة مناطق SMS—ولا ينبغي تركها مفتوحة افتراضياً—والحصول على موافقة المستخدم قبل إرسال رقم الهاتف إلى Firebase. يفرض Firebase أيضاً حدود إساءة استخدام لرسائل SMS، ويتيح أرقاماً تجريبية مخصصة للاختبارات غير الإنتاجية.

## ضوابط التكامل

| الخطوة | ضابط الحماية |
|---|---|
| طلب OTP | حد معدل لكل هاتف وجهاز، reCAPTCHA/App Verification، ورسالة موافقة واضحة. |
| تأكيد OTP | التطبيق يحصل على Firebase ID token فقط؛ لا يرسل رمز OTP أو يسجله خادمياً. |
| ربط العميل | الخادم يتحقق من ID token ويرفض عدم تطابق رقم Firebase مع رقم العميل المعياري. |
| الولاء والقسائم | التسعير يقرأ حساب العميل المقفل ويحد الخصم وفق البرنامج؛ لا يثق بقيمة نقاط من التطبيق. |
| التدقيق | يسجل الخادم معرف العميل والطلب والحركة المالية فقط، من دون رموز OTP أو Firebase tokens في السجلات. |

## إعدادات مطلوبة قبل الإطلاق

1. تسجيل تطبيق Android بالمعرّف الثابت `online.alarabiya.customerstore`، ثم تسجيل تطبيق iOS بالمعرّف نفسه عند توفر حساب Apple Developer، وحفظ ملفات الإعداد الرسمية في القنوات الآمنة.
2. تمكين Phone provider، وضبط سياسة بلدان SMS لتشمل العراق عند الحاجة فقط.
4. إضافة أرقام اختبار Firebase للبيئة غير الإنتاجية.
5. توفير معرّفات Firebase العامة للتطبيق ومفاتيح تحقق الخادم في إعدادات آمنة، لا في المستودع.
6. اختبار ربط Firebase ID token بالنظام الأساسي قبل تفعيل صرف النقاط أو القسائم.

### ملف Android

بعد تسجيل Android، ينزّل Firebase ملف `google-services.json`. يُحفظ هذا الملف في جذر مشروع التطبيق باسم `customer-store-mobile/google-services.json` ويُشار إليه من إعداد بناء Expo فقط. لا يحتوي الملف كلمة مرور أو مفتاح خادم؛ ومع ذلك لا تُستخرج منه مفاتيح إدارية ولا يُستخدم بدلاً من تحقق الخادم من Firebase ID token.

### بصمة Google Play للإصدار الداخلي

في 21 أغسطس 2026 أُضيفت بصمة SHA-256 الفعلية لشهادة **Google Play App Signing** إلى تطبيق Android في Firebase: `A4:E1:5F:58:9D:86:1F:B7:9E:6F:D5:E2:51:36:49:DA:F6:9D:B6:41:12:CE:E5:17:FB:21:A3:AD:2C:3A:7D:EE`. هذه البصمة مطلوبة لمسار Play Integrity عند تثبيت التطبيق من Google Play. يلزم إنشاء بناء جديد وتثبيته قبل إعادة اختبار إرسال الرمز.
