# خطة تنفيذ سوبر العربية عبر Expo

## قرار البنية

`expo/superapp-mobile` تطبيق مستقل عن `expo/customer-store-mobile` وعن `android-native`. يبقى تطبيق Android الأصلي خط الإنتاج المرجعي حتى تتحقق المساواة الوظيفية والأمنية. لا نشارك Firebase أو EAS project أو ملفات الاعتماد مع تطبيق العميل.

## الخريطة البصرية للتنفيذ

```mermaid
flowchart RL
  foundation["المعاينة المحلية\nRTL + المالك + الموظف"] --> transport["النقل الأصلي الآمن\nKeystore / Secure Enclave"]
  transport --> contracts["عقود خادم مصغرة\nصلاحية ونطاق من الخادم"]
  contracts --> journeys["مسارات الدور\nقرار · حضور · قسيمة · مهمة"]
  journeys --> native["قدرات أصلية\nإشعار · مسح · PDF · عدم اتصال"]
  native --> release["بوابة التكافؤ\nAndroid داخلي ثم TestFlight"]
  release --> production["قرار إنتاج منفصل\nلا يُفتح تلقائياً"]
```

كل سهم هو بوابة قبول: لا تنتقل البيانات الحقيقية أو العمليات الحساسة إلى المرحلة التالية قبل تحقق المرحلة السابقة على Android وiPhone.

| البيئة | Android | iPhone |
|---|---|---|
| تطوير | `online.alarabiya.store.expo` | `online.alarabiya.superapp.preview` |
| أثر متجر | `online.alarabiya.store`، versionCode `18`، للاختبار الداخلي بعد تحقق مفتاح الرفع | `online.alarabiya.superapp`، إعداد جاهز للبناء لاحقاً بعد تهيئة Apple Developer |

مشروع EAS مستقل باسم `@shrkh-alruyh-alarbyh/super-arabia` ومعرفه مثبت في التهيئة. ملف `store-ios` مهيأ ولا يرسل شيئاً تلقائياً. أما Android فيُبنى محلياً داخل GitHub Actions بالمفتاح الحالي ثم يرفع يدوياً إلى Internal testing فقط.

## 0. الأساس المنجز

- Expo SDK 54 + Expo Router + Development Build.
- توكنات تصميم RTL دلالية، لا تعتمد على اسم لون مضلل أو تدرجات واجهات تشغيلية.
- معاينة محلية صادقة لمركز قرار المالك؛ «يومي» يتصل فقط من Development Build موثق وبعد دخول أصلي.
- بوابات TypeScript وVitest وExpo Doctor وتهيئة التطبيق وحماية Metro من `image-size`.

## 1. وحدة النقل الآمن — مكتملة برمجياً وقيد إثبات الأجهزة

نبني `alrueya-secure-transport` كوحدة Expo أصلية بـKotlin وSwift. لا تكون دالة JavaScript تغلف `fetch`.

- مكتمل في Android: مفتاح P-256 غير قابل للتصدير، كوكي AES-GCM في Keystore، عداد/nonce وتوقيع canonical، وناقل يسمح بإجراءات مسماة فقط.
- مكتوب في iOS: Secure Enclave/Keychain، `biometryCurrentSet` للجلسة، URLSession يثبت SPKI بعد فحص TLS/hostname الافتراضي. يحتاج بناء Xcode وجهاز فعلي لإثباته.
- لا يرى TypeScript الكوكي أو الرمز أو الـnonce أو العداد أو pin؛ يستدعي فقط إجراءات مسمّاة ومراجعة: `login` و`twoFactor` و`logout` و`mobileToday` و`mobileAttendanceHistory` و`mobilePayslipReveal` و`mobileRequestLeave` و`mobileWithdrawLatestLeave` و`mobileStartFocusedTask` و`mobileResolveFocusedTask` و`mobileCommandCenter` وإجراءات إشعار Expo الثلاثة (`status` و`register` و`revoke`). لا يوجد جسر `fetch` أو URL حر. معرّف إعادة الطلب للإجازة والمهمة UUID عشوائي من الوحدة الأصلية، لا من JavaScript.
- Android يتطلب نافذة مصادقة نظامية قصيرة قبل فك الجلسة؛ iOS يطلب Keychain biometric عند القراءة. لا يحل أي منهما محل 2FA الخادمي.
- بناء الإنتاج يرفض endpoint غير آمن أو pin مفقود قبل التوليد.

**دليل القبول المتبقي:** login، lock/unlock، logout، revoke device، nonce replay، وpin mismatch على Android وiPhone فعليين. لا يعد الكود أو اختبار الوحدة دليلاً بديلاً.

## 2. عقود الخادم المتوافقة

لا نغير عقد Android الحالي فجأة.

1. نضيف client identity صريحة `superapp-expo` إلى `server/auth/deviceProof.ts` مع الحفاظ على `android-native` legacy.
2. اكتملت خدمة `mobileToday` وسجل الحضور الشخصي: تستقبلان `Actor` فقط، وتفرضان الدور والشركة والفرع وتاريخ بغداد من الخادم. لا تقبلان `employeeId` أو `branchId` أو تاريخاً من الهاتف، ولا يقبلهما tRPC إلا من جلسة `superapp-expo` مثبتة بالجهاز. سجل الحضور محدود بآخر 31 يوماً ويستبعد السعر والأجر والملاحظات ومصدر جهاز البصمة.
3. نعيد بيانات المالك من مركز القرار وبيانات الموظف من مساحة عمله، مع حالة توفر لكل مصدر؛ فشل `metrics.*` أو `alerts.*` لا ينتج صفراً.
4. لا تُرسل الرواتب الأساسية أو البدلات أو أي قسيمة لزميل ضمن bootstrap أو cache. القسيمة الشخصية تُفصح فقط بعد TOTP/رمز استرداد جديد يُستهلك خادمياً في كل فتح؛ لا تذكرة قابلة لإعادة الاستخدام ولا كلمة مرور متصفح.
5. طلب الإجازة وسحب آخر طلب معلّق هما أوامر Expo مقفلة: لا يقبلان `employeeId` أو `branchId` أو `leaveId` من الهاتف. الخادم يشتقها من الجلسة ويختم retry-key المرتبط بالموظف وبصمة الحمولة.
6. تبقى الاعتمادات والتسويات في شاشاتها المعتمدة مع maker-checker؛ بطاقة المنزل تفتح وجهة typed فقط.

**دليل القبول:** اختبارات نطاق المالك/مدير الفرع، موظف مرتبط/غير مرتبط، capabilities المحجوبة، وغياب الحقول الحساسة من الحمولة.

## 3. مسارات التطبيق حسب الدور

### المالك

1. مركز القرار: النطاق، وقت التحديث، 3 قرارات، توفر البيانات.
2. عرض تفاصيل القرار ثم الوجهة المسموحة للخادم.
3. نبض اليوم ومخاطر الذمم والخزينة والمخزون.
4. الاعتمادات والتقارير عبر شاشات التأكيد والتدقيق الحالية.

### الموظف

1. يومي: مكتمل للقراءة الشخصية: الحضور، المهمة، الإجازة، وحالة القسيمة فقط. لا مبالغ ولا سجل قديم ولا بيانات بديلة عند فشل النقل.
2. سجل الحضور: حالة صادقة عندما لا يصل جهاز البصمة أو يحتاج السجل مراجعة، مع PDF شخصي للفترة الخادمة المحددة. يولّد محلياً في cache خاص بالتطبيق، لا يُحفظ في التنزيلات، ويحذف بعد عودة ورقة المشاركة.
3. القسيمة: مكتمل برمز تحقق ثنائي خادمي جديد لكل فتح، ثم تصدير PDF شخصي محدود داخل cache التطبيق ومشاركة صريحة. لا يساوي فتح الجلسة أو بصمة الجهاز وحدهما تفويضاً لخادم الراتب، ولا تبقى قيمة الرمز في React بعد الطلب.
4. الإجازة: مكتملة كطلب ذاتي وسحب آخر طلب معلّق، بحالة نجاح/فشل قابلة للفهم وإعادة إرسال idempotent. لا اختيار موظف أو فرع أو سجل.
5. المهمة: مكتملة لمسار التركيز اليومي فقط: بدء أو إتمام المهمة التي يشتقها الخادم للحساب، مع retry-key idempotent لا يستطيع بعده اختيار مهمة تالية. تبقى إدارة طوابير المهام الواسعة داخل النظام الأساسي.

### مدير الفرع والموظفون التشغيليون

تظهر فقط الوحدات التي تسمح بها capabilities الخادمية؛ التنقل ليس سلطة. الإصدار الحالي لا يضيف مخزوناً أو مبيعات أو ماسحاً شكلياً: تبقى هذه العمليات في النظام الأساسي حتى يُعتمد عقد تشغيلي محدود لكل منها.

## 4. القدرات الأصلية

- **الإشعارات — مكتملة في الكود:** جداول `superAppExpoPushDevices` و`superAppExpoPushOutbox` مستقلة عن FCM القديم وتطبيق العميل، token مشفّر وبصمته SHA-256 فقط، تسجيل/إلغاء مسميان ومثبتان بمفتاح الجهاز، outbox durable مع retry وإلغاء `DeviceNotRegistered`. شاشة القفل عامة والوجهات الثلاث مغلقة. لا يبدأ الإرسال إلا بإعداد تشغيل صريح؛ يبقى اختبار جهاز Android وiPhone حقيقياً بوابة قبول.
- **المسح:** لا نعرض ماسحاً شكلياً قبل تحديد المسار التشغيلي والصلاحية. عند تفعيله سيكون `expo-camera` للباركود مع عقد تطبيع مشترك؛ HID/OCR يبقيان وحدات أصلية عند الحاجة. لا يعامل paste كمسح مفروض.
- **الملفات وPDF:** كشف الحضور والقسيمة الشخصيان مكتملان محلياً ومحدودان بالبيانات المعروضة بعد التفويض. يُنشأ كل ملف في cache خاص بالتطبيق، لا يُحفظ تلقائياً في التنزيلات، ويحذف بعد عودة ورقة المشاركة. لا روابط ثابتة ولا Basic Auth.
- **عدم الاتصال:** القرار الأمني الحالي هو عدم حفظ أي بيانات أعمال محلياً: لا attendance أو راتب أو قائمة مخزون أو مركز قرار. تبقى البيانات في ذاكرة React فقط، وتُمسح عند إغلاق التطبيق؛ PDF الشخصي cache قصير العمر يُحذف بعد المشاركة. لا توجد طوابير أفعال offline ولا بديل «نجاح لاحق» مضلل.
- **الرابط العميق:** لا Universal/App Links قبل association domain واختبارات spoofing. مسار ضغط الإشعار الداخلي وحده يعمل بقاموس ثلاثي مغلق ويرفض URL وID وquery؛ كل رابط خارجي مدخل غير موثوق وغير مفعل.

## 5. النظام البصري والحركة

- خلفية هادئة، أسطح بيضاء، مسافات 4/8/12/16/24، حقول 12px، بطاقات 16px، sheets 20px.
- القرار قبل المؤشر، والنطاق قبل الرقم، وحالة البيانات قبل القيمة.
- هدف لمس لا يقل عن 48px، ونص عربي Cairo، وأرقام/وقت معزولة عند مزج RTL وLTR.
- انتقال شاشة 160ms؛ تحديث نتيجة 180–220ms؛ sheet 220ms؛ مع إلغاء الحركة عندما يطلب النظام ذلك.
- 4 وجهات محتملة على الهاتف: الرئيسية، يومي، العمل، وحسابي. الخادم يحدد ظهور الثلاث الأولى؛ حسابي هو مخرج الدخول والخروج الدائم.
- جميع التواريخ والأوقات والمبالغ تعرض بأرقام لاتينية داخل واجهة عربية RTL، مع عزل bidi للقيم المختلطة وحساب مبالغ كسري دقيق دون تحويلات `Number` المفقِدة للدقة.
- عند الخلفية تُفصل شجرة الشاشات الحاملة للبيانات، وعند العودة يلزم فتح حماية الجهاز قبل إعادة جلب الحمولة.

## 6. بوابات الجودة والإصدار

### لكل Pull Request

```powershell
Set-Location expo/superapp-mobile
pnpm install --frozen-lockfile --ignore-workspace
pnpm check
pnpm test
pnpm lint
pnpm check:image-size-security
pnpm check:app-config
pnpm dlx expo-doctor
pnpm exec expo export --platform web
```

ثم بوابات النظام الأساسي: `pnpm check` و`pnpm check:guards` واختبارات الخادم ذات الصلة.

### قبل Android الداخلي وTestFlight

- Development Build لا Expo Go.
- اختبار Android جهاز/محاكي وiPhone فعلي بFace ID.
- اختبار login/2FA/lock/revoke/pin mismatch/push/غياب cache/RTL وخط 200%. يضاف اختبار المسح فقط بعد اعتماد عقده التشغيلي وصلاحياته، لا كعنصر شكلي.
- التقاط كل لقطة في `VISUAL_QA_MATRIX.md` ومقارنتها بالحالة المرجعية.
- لا يبنى أثر Android إلا من `main` أخضر وبعد مطابقة الحزمة والإصدار وABI وتوقيع مفتاح الرفع. لا يرقّى خارج Internal testing.
- profile iOS مهيأ فقط؛ لا رفع TestFlight أو App Store حتى اختبار iPhone فعلي وتهيئة Apple Developer.

## مخاطر معلنة

- iOS لا يقدم بديلاً مطلقاً لـAndroid `FLAG_SECURE`; نستخدم privacy overlay وإخفاء المحتوى الحساس، ولا ندعي منع لقطة الشاشة.
- تثبت الحيازة الحالية لمفتاح P-256، ولا تثبت Android Key Attestation خادمياً بعد. هذا مشروع أمني منفصل، لا ادعاء تسويقي.
- Windows يكفي لتطوير Android/web؛ اختبار iPhone يحتاج EAS أو Mac/Xcode وحساب Apple Developer.

## المتبقي قبل التوسّع بعد Android الداخلي

1. مشروع Expo المستقل مثبت في التهيئة. يبقى ربط اعتماد FCM v1 في EAS وبيئة الخادم ثم إثبات token/permission/`DeviceNotRegistered` على Android وiPhone؛ لا يوجد مفتاح أو token في المستودع.
2. اعتماد حالة استخدام المسح لكل دور قبل بنائه: صلاحية inventory من الخادم، تطبيع باركود مشترك، كاميرا فعلية، وحالة not-found/ambiguous صريحة. لا نخلط هذا مع تطبيق العميل أو نضع زر كاميرا غير عامل.
3. Android جهاز حقيقي قبل أي ترقية خارج Internal testing، وiPhone حقيقي قبل TestFlight، مع 2FA، القفل، pin mismatch، النص 200%، RTL، PDF، الإشعارات، والتأكد من عدم حفظ بيانات الأعمال بعد logout/revoke.
4. Universal/App Links فقط بعد association domain واختبارات spoofing؛ لا تُدخل في الإصدار الحالي بدعوى التكافؤ.
